# uav-planner

Сервис планирования и распределения беспилотных авиационных работ — кейс **Галс** (2026).

Этот файл — журнал того, что реализовано в коде, и как это запустить.

Постановка задачи и ответы экспертов (`docs/trebovania`), концепция решения, обзор методов
и план реализации (`docs/realization`), канбан-доска (`docs/code`) лежат **вне этого
репозитория** — в общем дереве проекта, рядом с ним. Ссылки на них по тексту даны
относительно того дерева и из репозитория сами по себе не открываются.

## Статус проекта на сегодня

- **Код** (этот репозиторий) — продукт собирается и запускается целиком одной
  командой `docker compose up --build`: SPA за nginx, API, фоновый воркер, планировщик
  периодических задач, PostgreSQL с PostGIS и Redis. Сквозной сценарий работает от
  загрузки обстановки до выгрузки KML/GeoJSON подтверждённого плана — все шесть экранов
  интерфейса. 287 тестов.
- **Что именно реализовано.** Расчётное ядро: «Проекция и рабочая область», «Высота
  съёмки H», «Декомпозиция на ячейки», кластеризация по площадкам с TSP-туром и
  балансировкой (`routing`), обход запрещённых зон на переходах (`visibility`), расписание
  со световым днём (`schedule.timeline`), энергобюджет (`fleet.energy`), независимая
  «Проверка безопасности» (семь критериев, с координатами нарушений). Вокруг него —
  слоистый бэкенд с хранилищем в PostGIS, фоновый расчёт с прогрессом, отменой и лимитом
  времени, подтверждение и экспорт плана. Подробности по модулям — в разделе «Реализовано»
  ниже, вместе с честно документированными упрощениями первой версии (одна модель БВС на
  план, ветер без направления, автопересчёт без адаптации параметров).
- **Стоимость расчёта выросла.** Перебор кандидатов «модель + камера» и A* на каждом
  переходе означают, что конвейер выполняется столько раз, сколько подходящих групп.
  На тестовых сценах это доли секунды, на реалистичной сцене Екатеринбурга
  (21 объект обстановки, 13 бортов, три базы, область ~90 км²) — около 43 секунд.
  Лимит 1800 с из теоретического стал достижимым, а «лучшее найденное решение» при
  остановке по лимиту по-прежнему не сохраняется (см. «В работе / далее»).
- **Документация** (`docs/realization`): изучены ТЗ и ответы экспертов; написаны концепция
  решения, обзор методов (с обоснованием по статье Wang et al., 2025) и план реализации
  (роли, график 16–29.09, тест-матрица T1–T14, риски).
- **Открытые неточности ТЗ зафиксированы** как принятые допущения (раздел «Открытые
  неточности» в [`uav_planner_plan.html`](../docs/realization/uav_planner_plan.html#process)) —
  без них к реализации не приступаем, чтобы не блокироваться на ответах экспертов.
- **Канбан-доска** (`docs/code/uav_planner_kanban.html`) — задачи по обеим ролям (математика,
  интерфейсы) разнесены по этапам 0–4, с отражением текущего статуса выполнения.
- **Требования** (`docs/trebovania`) — функциональные требования по модулям в
  формате техзадания, отдельные документы по интерфейсу (`Интерфейс.md`) и
  полной математической модели алгоритма (`Математическая_модель.md`).

```

    domain/          # общий словарь: ошибки предметной области
    db/              # движок, сессия запроса, конверсия shapely <-> PostGIS
    models/          # ORM-модели (см. «Хранилище» ниже)
    repositories/    # единственное место, знающее, где лежат данные

    api/

      deps.py        # X-User-Name
      routers/       # HTTP: разбор запроса, коды ответов
      schemas/       # pydantic-схемы запросов и ответов
    geometry/ camera/ coverage/ routing/ visibility/ fleet/ safety/ schedule/
                     # чистая математика: ни HTTP, ни БД, ни глобального состояния
  tests/
  scripts/dump_openapi.py      # схема OpenAPI из объекта приложения (для типов SPA)
  web/                         # SPA: React + TypeScript + Vite за nginx
    PARITY.md                  # чек-лист паритета с прежним интерфейсом (закрыт)
    openapi.json, src/api/schema.d.ts   # снимок схемы и сгенерированные из неё типы
    src/app/                   # каркас: шапка, степпер, слоты панели и легенды
    src/map/                   # одна карта Leaflet на всё приложение, слои как компоненты
    src/features/              # экраны по модулям ТЗ
```

Слои разделены так: роутеры знают про HTTP, сервисы — про требования модулей,
репозитории — про хранилище, математика не знает ни о чем из этого. Поэтому
замена хранилища или способа запуска расчета не затрагивает формулы. Процесс API
не отдаёт ничего, кроме API и `/docs`: фронтенд собирается отдельно и живёт в
контейнере `web`.

## Запуск

### Через docker compose (основной способ)

```bash
docker compose up --build
```

Поднимает семь сервисов: `db` (PostGIS), `redis`, одноразовый `migrate`
(`alembic upgrade head`), `api`, `worker` (фоновый расчёт), `beat`
(периодические задачи) и `web` (SPA за nginx). Ничего ставить на хост не нужно.

**Интерфейс — `http://127.0.0.1:8080/`.** Он же проксирует `/api` на контейнер
`api`, поэтому фронтенд и API живут на одном origin и CORS не нужен. OpenAPI —
`/docs` на порту API, проверки состояния — `/api/health` (liveness) и
`/api/health/ready` (БД и Redis). Порт API наружу публикуется только
dev-надстройкой, для `/docs` и `curl`.

Если стандартные порты на машине заняты:

```bash
WEB_PORT=8081 API_PORT=8099 DB_PORT=55433 docker compose up --build
```

Холодный старт с нуля: `docker compose down -v && docker compose up --build`
(том БД пустой → миграции накатываются заново → приложение поднимается).

Настройки — переменные с префиксом `GALS_`, см. `.env.example` (файл
необязателен: у compose есть значения по умолчанию).

`api`, `worker`, `beat` и `migrate` — **один и тот же образ**, различается только
команда. Воркер масштабируется независимо (`docker compose up --scale worker=3`);
`beat` — ровно одна реплика, иначе расписание тикало бы кратно числу копий.

### Хранилище

Данные лежат в PostgreSQL с PostGIS: обстановки с объектами по слоям, парк БВС,
задачи, версии планов с вылетами, отчеты проверки безопасности, записи фоновых
расчётов и журнал выгрузок. Схема — в `migrations/`, накатывается сервисом
`migrate` при запуске compose.

Геометрия загруженных данных (объекты обстановки, область задачи) хранится
дважды: сырой GeoJSON в `jsonb` — это то, что возвращает API, вместе со
служебными свойствами `_valid`/`_buffer_geojson` и любыми полями из файла
оператора; и `geometry(...,4326)` — индексируемая копия для пространственных
запросов. Круг через PostGIS нормализует геометрию (теряет обертку Feature и
негеометрические члены), поэтому отдавать наружу нормализованную копию нельзя.
Маршруты и галсы вылетов, наоборот, порождаются нами, поэтому хранятся только
как geometry и читаются через shapely — не через `ST_AsGeoJSON`, который
обрезает координаты до девяти знаков.

**Миграции, меняющие смысл уже сохранённых данных, не додумывают за человека.** Их в
цепочке четыре, и каждая честно останавливается, когда ответа нет:

- `0005` (парков много) — имя старым паркам выводится из даты загрузки, а вот координаты
  не из чего: колонка появляется этой же ревизией. Ноль отправил бы парк в Гвинейский
  залив и дал молча неверный расчёт, поэтому накат прерывается с объяснением, что сделать.
- `0006` (у задачи свой парк) — парк проставляется, только если он в системе ровно один:
  тогда ответ единственный. При нескольких выбор за человеком.
- `0007` (этапы вылета) — старым планам этапы не восстановить, они считались без них;
  пустой список честнее выдуманного разбиения.
- `0008` (структурные нарушения) — тип колонки не меняется, но содержимое переводится из
  строк в объекты, иначе чтение падает на первом же старом отчёте. Координат у старых
  нарушений нет и взять их неоткуда: маркер просто не появится, текст сохраняется.

Проверено: данные переживают `docker compose restart api worker beat` (обстановка,
задача, все версии планов с геометрией маршрутов, отчеты проверки и записи
фоновых расчётов на месте), а автопересчет при нарушении по-прежнему создает
версии 2-4 и один отчет на семь критериев.

### Фоновый расчёт

Расчёт плана (ПЛН.ФТ.5) и проверка безопасности с автопересчётом (БЕЗ.ФТ.3)
выполняются в отдельном сервисе `worker` через Celery поверх Redis. Состояние
работы — строка в таблице `plan_jobs`: статус («В очереди», «Выполняется»,
«Завершен», «Остановлен по лимиту времени», «Ошибка», «Отменен»), стадия
конвейера, процент, ссылка на готовый план или отчёт.

**Запуск расчёта отвечает гибридно.** `POST /api/plans` ставит работу в очередь
и до `wait_s` секунд (`GALS_PLAN_SYNC_WAIT_SECONDS`, по умолчанию 30 в dev, 0 в
проде) ждёт её завершения: успел — прежний `200 PlanSummary`, не успел — `202`
с объектом работы и заголовком `Location: /api/plan-jobs/{id}`. Так сцены
тестового масштаба, которые считаются за доли секунды, не требуют от клиента
поллинга, а в проде эндпоинт всегда отдаёт 202. То же — у
`POST /api/safety-checks`.

Эндпоинты работы:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/plan-jobs/{id}` | статус, стадия, процент, ссылки на результат |
| `GET` | `/api/plan-jobs?task_id=` | все работы задачи — переподключение индикатора после перезагрузки вкладки |
| `POST` | `/api/plan-jobs/{id}/cancel` | отмена расчёта (ПЛН.ФТ.5) |

Устройство, в трёх решениях:

- **Прогресс пишется своей короткой транзакцией и сразу коммитится.** Внутри
  длинной транзакции расчёта он не был бы виден снаружи до самого конца — то
  есть до конца получасовой работы. Тем же запросом
  (`UPDATE ... RETURNING cancel_requested`) читается флаг отмены, поэтому
  проверка отмены не стоит отдельного обращения к БД.
- **Отмена кооперативная, с двумя страховками.** Флаг проверяется на каждой
  границе стадии; работу, ещё не взятую воркером, снимает `revoke`; если через
  `GALS_CANCEL_GRACE_SECONDS` работа всё ещё идёт, отложенная задача снимает её
  сигналом. Отдельно: воркер переводит работу в «Выполняется» **условным**
  `UPDATE` — `revoke` широковещателен и до выключенного воркера не доходит,
  поэтому сообщение отменённой работы, доставленное после его перезапуска,
  отсеивается по строке и расчёт не начинается вовсе.
- **Одна активная работа на задачу** — частичный уникальный индекс. Это защита
  от двойного клика по «Рассчитать»; ретрай сети закрывает заголовок
  `Idempotency-Key`. Ключ идемпотентности по умолчанию **не** хеш параметров:
  ПЛН.ФТ.4 требует, чтобы повторный расчёт неизменённой задачи создавал новую
  версию плана.

**Janitor: работа, чей воркер погиб.** Контейнер воркера может умереть посреди
расчёта — тогда строка остаётся «Выполняется», а обновлять её больше некому.
Такие работы добивает периодическая задача `gals.sweep_stale_jobs`: раз в
`GALS_JOB_SWEEP_INTERVAL_SECONDS` (30 с) она одним `UPDATE` переводит в «Ошибка»
всё, что числится «Выполняется» без heartbeat дольше
`GALS_JOB_STALE_AFTER_SECONDS` (120 с), с текстом «расчёт прерван перезапуском
сервиса». Ставит её в очередь отдельный сервис `beat`, выполняет обычный воркер.

Статус «В очереди» сторож не трогает намеренно: очередь переживает перезапуск
(Redis с `appendonly`), и долгое ожидание в ней — норма, а не смерть воркера.

Это отдельный процесс, а не проверка в пути чтения, и разница существенная.
Ленивый сторож означал, что исход работы появляется, только если кто-нибудь в
неё заглянет: получасовой расчёт оператор вполне может запустить и уйти, а
тогда работа так и остаётся «Выполняется» — и по ней нельзя ни построить
отчёт, ни увидеть, сколько расчётов унёс очередной перезапуск. Плата за перенос
одна: осиротевшая работа опознаётся не мгновенно, а с задержкой до одного тика
janitor'а.

Что проверено на живом стенде, а не только тестами: постановка в очередь и
опрос статуса реальным воркером; прогресс, записанный процессом воркера, виден
API немедленно (стадии 3 → 20 → 30 → 75 → 96 %); отмена работы в очереди при
остановленном воркере с последующим отказом выполнить её после перезапуска;
переживание `docker compose restart api worker beat`; холодный старт
`down -v && up --build`; и полный сценарий janitor'а — воркер заморожен
SIGSTOP посреди расчёта (стадия «Декомпозиция области», 30 %), убит SIGKILL,
работа осталась «Выполняется», через 121 с после перезапуска переведена в
«Ошибка» с `error_code = interrupted`. Заодно подтвердилось обратное правило:
две работы, простоявшие в очереди при мёртвом воркере, janitor не тронул и они
были рассчитаны после его подъёма.

Ограничение, честное для текущей версии: остановка по лимиту времени (ПЛН.ФТ.3)
фиксируется статусом и сообщением, но лучшее найденное решение не сохраняется —
конвейер эвристик не имеет промежуточного допустимого плана. Он появится вместе
с решателем OR-Tools, умеющим отдавать incumbent по `time_limit`. По той же
причине лимит недостижим живой сценой: сцена вчетверо крупнее ориентира ТЗ
(100 км² / 10 БВС) считается за десятые доли секунды, поэтому исходы «лимит» и
«внутренний сбой» покрыты тестами с подменой расчёта, а не прогоном.

### Журнал

Один формат на все процессы: в разработке — читаемая строка, в остальных
окружениях — по строке JSON на запись (`GALS_LOG_FORMAT=auto|json|text`,
уровень — `GALS_LOG_LEVEL`). `uvicorn` и `celery` по умолчанию ставят свои
обработчики со своим форматом, поэтому они разоружаются и отдают записи общему
корневому — иначе в одном потоке контейнеров живут три разных формата сразу.

```json
{"ts": "2026-09-21T09:27:54.415Z", "level": "INFO", "logger": "uav_planner.jobs.tasks",
 "message": "расчет завершен", "job_id": "3bd3d804-…", "task_id": "6bf75ee2-…",
 "kind": "plan", "job_status": "Завершен", "duration_s": 0.021}
```

**Корреляция — через `ContextVar`, рядом с сессией БД.** Идентификаторы не
передаются аргументом в каждую функцию: их кладёт в контекст тот, кто владеет
границей (middleware — для запроса, задача воркера — для работы), а в запись их
подмешивает фильтр. Поэтому строку, сделанную сервисом или репозиторием,
всё равно можно выбрать по `job_id` — хотя эти слои о журнале ничего не знают.
Половина пользы от журнала получасового расчёта именно в этом: выбрать строки
одной работы из общего потока.

Поля контекста:

| поле | откуда | зачем |
|---|---|---|
| `request_id` | заголовок `X-Request-Id` или свой; возвращается в ответе | связать строку в журнале браузера со строкой в журнале сервиса |
| `job_id` | задача воркера | все строки одного фонового расчёта |
| `task_id`, `kind` | строка `plan_jobs` | все расчёты одной задачи, включая автопересчёты БЕЗ.ФТ.3 |

Границы, на которых пишется запись: приём запроса (DEBUG) и его исход с кодом и
длительностью (INFO); постановка работы в очередь и запрос отмены; старт и исход
фонового расчёта с длительностью; автоматический пересчёт при нарушении; смена
статуса плана (проверен, подтверждён, отказ по конфликту ЭКС.ФТ.9) и выгрузка.
Строка доступа `uvicorn` отключена — её заменяет своя, с идентификатором и
исходом; проверки состояния идут уровнем ниже, иначе опрос `/api/health` каждые
15 с вытеснил бы из INFO всё остальное.

### Локально, без Docker

```bash
python -m venv .venv
.venv/bin/pip install -e ".[dev]"      # Linux/macOS
# .venv/Scripts/python.exe -m pip install -e ".[dev]"   # Windows
.venv/bin/python -m pytest -q
```

Тестам нужен настоящий PostGIS (в схеме geometry-колонки и частичные индексы,
SQLite не подходит). База берется из `GALS_TEST_DATABASE_URL`, иначе
поднимается контейнером через testcontainers; если нет ни того, ни другого —
тесты с пометкой `db` пропускаются, а 115 тестов, которым БД не нужна, идут как
обычно (`pytest -m "not db"` — быстрый цикл без Docker вовсе). Всего тестов 246.

### Интерфейс

Интерфейс — SPA в `web/` (React + TypeScript + Vite), раздаётся nginx'ом в
контейнере `web` и открывается на `http://127.0.0.1:8080/`. Первая версия
интерфейса (одностраничный `static/index.html` внутри пакета) удалена тем же
коммитом, что закрыл последний пункт [`web/PARITY.md`](web/PARITY.md); процесс
API больше не отдаёт ничего, кроме API и `/docs`, и на это есть тест — если
корень снова начнёт отдавать HTML, значит в образ опять попала статика.

Разработка фронтенда без пересборки образа:

```bash
cd web && npm install && npm run dev      # http://127.0.0.1:5173
```

Dev-сервер проксирует `/api` туда же, куда nginx, — на поднятый compose
(`VITE_API_TARGET=http://127.0.0.1:8000` по умолчанию). Типы API берутся из
схемы: `npm run schema` снимает `openapi.json` с объекта приложения и
регенерирует `src/api/schema.d.ts`; оба файла закоммичены. Рассинхрон фронта с
бэком ловится `npm run schema && git diff --exit-code` — пока вручную: CI в
репозитории ещё нет (см. «В работе / далее»).

Тестовые сцены для загрузки — `examples/`:
- `scene_valid.geojson` — корректная обстановка под Москвой (2 ВПП, резервная площадка, БПЗ
  с буфером, препятствие) — экран обстановки со статусом «Корректна».
- `scene_valid_2.geojson` — вторая, независимая корректная обстановка под Санкт-Петербургом
  (1 ВПП, 2 резервные площадки, БПЗ с буфером, препятствие) — удобно загрузить её после
  `scene_valid.geojson`, чтобы проверить «+ Загрузить ещё одну обстановку»
  и переключение между несколькими загруженными обстановками в истории.
- `scene_with_errors.geojson` — обстановка под Москвой с четырьмя намеренными ошибками
  (самопересекающийся полигон БПЗ, препятствие без верхней границы высоты, ВПП внутри буфера
  БПЗ, резервная площадка за пределами разрешенного пространства) — показывает панель ошибок
  и блокирует переход к задаче.
- `fleet_valid.json` — корректный парк из 7 экземпляров, все три модели Геоскан вперемешку
  со статусами (5 «Готов», 1 «Недоступен», 1 «На обслуживании»; `base_launch_site` совпадает
  с наименованиями ВПП из `scene_valid.geojson`) — загрузить в модуле «Парк БВС», чтобы затем
  рассчитать план по задаче: несколько готовых экземпляров одной модели (Gemini, 801)
  позволяют увидеть распределение галсов между двумя-тремя БВС, а не одним.

Об образах: бэкенд — многостадийный `Dockerfile` от непривилегированного
пользователя, один и тот же образ у `api`, `migrate`, `worker` и `beat`,
различается только команда. Фронтенд — свой многостадийный `web/Dockerfile`
(node собирает, nginx раздаёт), в рантайме ни node, ни `node_modules` не
остаётся.

## Реализовано

### `uav_planner.geometry` — проекция и рабочая область

#### `projection.py`

- **`utm_crs_for(lon, lat) -> CRS`** — считает номер зоны UTM (`int((lon+180)//6)+1`) и
  возвращает CRS `WGS 84 / UTM zone N` или `...S` (EPSG 326xx/327xx) в зависимости от
  знака широты. Чистая функция, без сети.
- **`Projector`** — держит пару трансформаций `pyproj.Transformer` (WGS-84 → UTM и обратно)
  для одной, уже выбранной, зоны:
  - `Projector.for_point(lon, lat)` — фабрика: строит проекцию для зоны, в которую
    попадает точка.
  - `Projector.for_geometry(geom)` — то же самое, но зона выбирается по центроиду
    геометрии (полигона области, парка ВПП и т. п.) — так весь расчет сцены идет в одной
    системе координат.
  - `.to_utm(geom)` / `.to_wgs84(geom)` — прогоняют shapely-геометрию (точку, полигон,
    мультиполигон — что угодно) через `shapely.ops.transform` с сохранением порядка осей
    `(x, y)` = `(lon, lat)` / `(easting, northing)`, т. е. без путаницы lat/lon, характерной
    для proj4 по умолчанию.

#### `area.py`

- **`HeightRange(h_min, h_max)`** — диапазон высот, датакласс с проверкой `h_min <= h_max`
  в `__post_init__`; метод `.contains(h)` — попадает ли высота в диапазон.
- **`TimeWindow(start, end)`** — интервал действия зоны (даты/время); тот же принцип:
  проверка порядка в `__post_init__`, метод `.contains(when)`.
- **`AllowedZone(id, polygon, height, active_windows=None)`** — зона разрешенного
  воздушного пространства: полигон + диапазон высот + (опционально) список `TimeWindow`.
  `.is_active_at(when=None)` — активна ли зона в момент `when`; без интервалов или без
  переданного `when` зона считается активной всегда (консервативно).
- **`NoFlyZone(id, polygon, safety_buffer_m=0.0, active_windows=None)`** — бесполетная
  зона. `.footprint()` — контур зоны, раздутый на `safety_buffer_m` (если буфер задан) —
  именно эта раздутая форма вычитается из рабочей области, а не исходный полигон.
  `.is_active_at()` — как у `AllowedZone`.
- **`Obstacle(id, polygon, height, safety_buffer_m=0.0)`** — высотное препятствие,
  «призма» полигон + `[h_min, h_max]`. `.footprint()` — контур с буфером (как у
  `NoFlyZone`). `.is_hole_at(survey_height_m, margin_m=0.0)` — булев признак: становится
  ли препятствие дырой в рабочей области при заданной съемочной высоте H — истина, если
  `h_max + margin >= survey_height_m` (объект не ниже уровня съемки, даже с запасом).
- **`validate_polygon(geom) -> geom`** — проверяет, что геометрия не пустая и
  `geom.is_valid`; на невалидной геометрии (в т. ч. самопересекающийся контур — по
  определению OGC/shapely это уже невалидность) бросает `GeometryError` с текстом причины
  из `shapely.validation.explain_validity`. Возвращает ту же геометрию — удобно для
  `assert validate_polygon(g) is g` и для использования в цепочке вызовов.
- **`safe_simplify(polygon, tolerance_m, safety_buffer_m) -> geom`** — упрощение контура
  алгоритмом Дугласа — Пекера (`shapely.simplify(..., preserve_topology=True)`), но
  сначала проверяет `tolerance_m < safety_buffer_m` и бросает `ValueError`, если это не
  так — иначе упрощенный полигон может выйти за пределы буфера безопасности зоны.
- **`compute_working_area(survey_area, allowed_zones, no_fly_zones, obstacles, survey_height_m, obstacle_margin_m=0.0, when=None) -> geom`**
  — основная функция модуля, считает рабочую область по формуле
  `(Область ∩ Разрешенное) − БПЗ − препятствия выше H`:
  1. проверяет `survey_area` через `validate_polygon`;
  2. если заданы `allowed_zones` — оставляет только те, что покрывают `survey_height_m`
     по высоте и активны в момент `when`, объединяет их (`unary_union`) и пересекает с
     областью; если ни одна зона не подошла — бросает `GeometryError` (высота съемки не
     покрыта разрешенным пространством);
  3. вычитает `footprint()` всех активных `NoFlyZone`;
  4. вычитает `footprint()` всех `Obstacle`, для которых `is_hole_at(H)` истинно.
  Вычитание (внутренняя `_subtract_footprints`) строит `STRtree` по зонам-кандидатам и
  запрашивает только реально пересекающие рабочую область (`predicate="intersects"`) —
  не гоняет `.difference()` по зонам сцены, которые область не касаются.

#### `errors.py`

- **`GeometryError(ValueError)`** — единственное исключение модуля: невалидная/пустая
  геометрия, самопересечение, высота съемки не покрыта разрешенным пространством. Отдельный
  тип, чтобы вызывающий код (API, проверка безопасности) отличал ошибку геометрии от прочих
  `ValueError`.

Все геометрии внутри модуля — в проекции UTM (метры); вход/выход сервиса — WGS-84
(перевод — через `Projector`). Принятые допущения по неточностям ТЗ — в
[`uav_planner_plan.html#process`](../docs/realization/uav_planner_plan.html#process).

Тесты: `tests/test_projection.py`, `tests/test_area.py` — 18 тестов, покрывают выбор зоны UTM
(север/юг, границы), обратимость проекции, сохранение площади, вычитание БПЗ, дыры от
препятствий, интервалы действия по времени, защиту `safe_simplify`.

### `uav_planner.camera` — высота съемки H и шаг галсов d

- **`specs.py`** — справочник камер `CAMERA_SPECS` (фокусное расстояние, размер матрицы,
  разрешение кадра) и справочник моделей БВС `UAV_MODELS` (высотный диапазон
  `UavHeightLimits`, совместимые камеры) для трёх моделей Геоскан (201, Gemini, 801).
  Функции `is_height_allowed(uav_model_key, height_m)` и
  `is_camera_compatible(uav_model_key, camera_key)` — проверки допустимости связки.
  Для Sony RX1RM2 и PF1B параметры паспортные; для Pollux, тепловизора 640×512 и
  RGB-камеры 12 Мп (801) — оценка по типовым сенсорам такого класса, помечена
  `verified=False` (см. допущение в [плане реализации](../docs/realization/uav_planner_plan.html#process)).
- **`optics.py`** — формулы: `survey_height(camera, gsd_cm)` — высота по целевому GSD
  (`H = GSD·f·N_w/s_w`); `swath_width()`/`footprint_length()` — ширина полосы захвата и
  длина кадра вдоль трека на заданной высоте; `track_spacing()`/`trigger_spacing()` — шаг
  между галсами и шаг срабатывания камеры при заданном перекрытии (с проверкой, что
  перекрытие в `[0, 1)`). `plan_survey_geometry(uav_model_key, camera_key, gsd_cm, ...)` —
  собирает всё в `SurveyGeometry`, предварительно проверив совместимость камеры с моделью
  и попадание расчётной H в высотный диапазон модели; иначе — `CameraError`.
- **`errors.py`** — `CameraError(ValueError)`.

Тесты: `tests/test_camera.py` — 13 тестов; для RX1RM2 и PF1B расчётные H/B/d сверены с
контрольной таблицей концепции (раздел 3) с допуском 5% и совпадают; для Pollux — тот же
расчёт с допуском 20% (нет паспортных данных сенсора); плюс проверки границ высотных
диапазонов моделей, совместимости камер и отказов `plan_survey_geometry`.

### `uav_planner.coverage` — декомпозиция области на ячейки и галсы

- **`direction.py`** — `best_sweep_direction(polygon, wind_bearing_deg=None, wind_penalty_weight=0.15)`:
  минимальная ширина по выпуклой оболочке (Huang, 2001) — перебираются направления
  только вдоль сторон оболочки (вращающиеся калиперы), так как для выпуклой фигуры
  оптимум доказанно достигается на одной из них. С заданным `wind_bearing_deg`
  штрафует направления с сильной поперечной составляющей ветра:
  `cost = width · (1 + wind_penalty_weight · crosswind_fraction)`. `crosswind_fraction()` —
  доля ветра поперек галсов (0 — вдоль, 1 — строго поперек).
- **`cells.py`** — `Cell(polygon, direction_deg)` и `boustrophedon_cells(area, wind_bearing_deg=None, min_cell_area_m2=1.0)`.
  Режет рабочую область горизонтальными полосами (в системе координат, повёрнутой так,
  что общее для всей области направление слайсинга совпадает с осью X) по критическим
  Y — координатам вершин полигона и его дыр; полосы с одинаковой связностью объединяет
  в одну ячейку (без явной классификации событий IN/OUT/split/merge, но с тем же
  результатом, что у классической boustrophedon cellular decomposition Choset & Pignon,
  1997). Каждая полученная ячейка не содержит внутренних дыр; направление галсов внутри
  неё выбирается заново — по минимальной ширине именно этой ячейки, а не всей области.
  `min_cell_area_m2` отсекает численный мусор — тонкие сколы на вершинах. Мультиполигон
  обрабатывается по частям (они физически не связаны).
- **`tracks.py`** — `generate_tracks(cell, spacing_m)`: параллельные галсы с шагом
  `spacing_m` вдоль `cell.direction_deg`, каждый обрезан по фактической границе ячейки
  через пересечение (не по прямоугольной оценке) — если ячейка не идеально выпукла в
  выбранном направлении, для одной позиции вернётся несколько отрезков вместо одного;
  область всё равно покрыта полностью и без выхода за её пределы, это не ошибка, а
  корректный случай. `split_long_track(track, max_len_m)` — режет галс на равные части
  не длиннее `max_len_m` (нарезка на вылеты — позже, в `routing`, но лимит длины участка
  общий).
- **`errors.py`** — `CoverageError(ValueError)`.

Тесты: `tests/test_direction.py`, `tests/test_cells.py`, `tests/test_tracks.py`,
`tests/test_coverage_integration.py` — 21 тест. Проверяют: выбор направления вдоль
длинной стороны прямоугольника и его поворот вместе с фигурой; штраф за ветер,
переключающий выбор направления при близких по ширине вариантах; декомпозицию
прямоугольника с дырой (ячейки без дырок, без перекрытий, суммарная площадь
сохраняется), мультиполигон (покрыты обе несвязные части), фильтрацию сколов
`min_cell_area_m2`; генерацию галсов для повёрнутой ячейки (курс совпадает с
направлением ячейки), разбиение галса на несвязные отрезки на невыпуклых (L- и
U-образных) ячейках, сохранение суммарной длины при `split_long_track`; и сквозной
прогон `geometry.compute_working_area → coverage.boustrophedon_cells → generate_tracks
→ split_long_track` на сцене с бесполетной зоной.

  проверка: обстановка существует и корректна; тип съемки и GSD (ЗАД.ФТ.4); критерий и вес
  α для «Компромисса» (ЗАД.ФТ.5); начало окна работ не позже конца (ЗАД.ФТ.3, блокирующая
  часть); валидность полигона области и его пересечение с объединением зон разрешенного
  пространства обстановки через `geometry.Projector` (ЗАД.ФТ.2). `_daylight_warning()` —
  предупреждение (не блокирует сохранение), если окно работ не пересекается со световым
  днем (`schedule.daylight_window_utc_hours`) для координат центроида области и даты —
  вторая, неблокирующая часть ЗАД.ФТ.3.
  `_check_fleet_environment_compatibility()` — проверка по запросу пользователя: парк и
  обстановка должны быть географически близко (порог 150 км по геодезическому расстоянию,
  `geometry.geodesic_distance_m` — локальная UTM-проекция на масштабе разных городов уже
  непригодна), иначе БВС физически не долетят до области работ. Представительная точка
  обстановки — центроид её валидных зон разрешённого пространства
  (`environment_service.environment_location`); если таких зон нет, проверка пропускается,
  а не падает — это уже другая ошибка. Парк задачи после создания не меняется: он часть
  постановки, как и обстановка. `create_task()`/`update_task()` — второй проверяет
  `expected_version == текущая версия`, иначе `TaskConflictError` с именем того, кто
  изменил запись (ЗАД.ФТ.12); редактирование запрещено только для статуса «Подтверждена».
  `mark_confirmed()` — переводит задачу в этот статус при подтверждении плана (ЭКС.ФТ.6);
  новый расчёт снова разблокирует правку, подтверждение относится к версии плана, а не
  запрещает считать новые.
- **`api/routers/tasks.py`** — `POST/GET /api/tasks`, `GET/PUT /api/tasks/{id}` (`POST` —
  form-data с обязательным `fleet_id`, `PUT` — с `expected_version`); область облета всегда передается на сервер файлом
  (`area_file`) — бэкенду не важно, собран ли этот файл загрузкой или рисованием на
  клиенте, проверки ЗАД.ФТ.2 одинаковы для обоих способов.

**Обертка файла области снимается на входе.** Редакторы карт (QGIS, geojson.io) сохраняют
нарисованный контур как `FeatureCollection`, реже — как `Feature`; сервисы и хранилище
работают с голой геометрией (`shape(task.area)` зовут и расчет, и проверка безопасности, а
рядом с сырым jsonb лежит индексируемая `geometry(4326)`). Поэтому роутер разворачивает
обертку один раз, а коллекцию из нескольких объектов отклоняет: область облета по ЗАД.ФТ.4
одна, и молча взять из файла первый попавшийся полигон хуже, чем сказать об этом.
Всё остальное, что может оказаться в чужом файле, — ошибка ввода `400`, а не отказ сервиса:
`shapely` падает на каждом виде мусора своим исключением (`GeometryTypeError` на
неизвестном `type`, `KeyError` без `coordinates`, `AttributeError` без `type` вообще), и
все они перехватываются как одна проблема поля `area`.

Экран — в SPA (`web/src/features/task/`), включая рисование области кликами по карте
(ЗАД.ФТ.9а–9б).

Тесты: `tests/test_api_tasks.py` — 25 тестов, включая пересечение с разрешенным
пространством, самопересечение полигона области (нашёл и исправил падение с необработанным
`GEOSException` — невалидная геометрия попадала в `unary_union` вместо того, чтобы быть
отфильтрованной), обязательность веса α для «Компромисса», окно работ «конец раньше
начала», предупреждение о полярной ночи, редактирование с правильной/устаревшей версией
(200/409) и имя пользователя в сообщении о конфликте, а также все формы файла области:
`FeatureCollection` с одним полигоном принимается и хранится развёрнутым, коллекция из
нескольких объектов и любой мусор дают `400`, а не `500`. Плюс совместимость парка и
обстановки: неизвестный парк, парк за 1400 км и парк в том же регионе.

### Модуль «Парк БВС»

Реализует `docs/trebovania/Парк_БВС.md` (ПБС.ФТ.2–4, ПБС.ФТ.5–11). Модуль не привязан к

экземпляра, загрузка отвергается: расчёт строит точку взлёта по ним, и парк без локации
непригоден.

- **`api/schemas/fleet.py`** — `FleetInstance` (с `valid`/`error` на уровне записи —

  `FleetSummary`/`FleetDetail` (имя, локация, подпись расположения), `ModelSpecOut`.
- **`services/fleet_service.py`** — `_parse_records()` принимает и JSON-массив, и CSV

- **`api/routers/fleet.py`** — `POST /api/fleets` (имя, необязательная подпись расположения,

### `uav_planner.routing` — кластеризация по площадкам, TSP-тур, балансировка

Распределение галсов по бортам и разбиение на вылеты. Первая версия использовала
LPT-эвристику и не учитывала переходы вовсе; сейчас — схема «взвешенный K-Means с
фиксированными центроидами + m-TSP внутри кластера + балансировка узкого места + Split»
(Математическая модель, разделы 10–11).

- **`cluster.py`** — `Vehicle` (id, скорость, бюджет вылета, **точка взлёта**), `Track`
  (галс в метрах UTM), `Sortie`, `RoutingResult`.
  `cluster_assign_and_route(tracks, vehicles, ...)`:
  1. **Кластеризация.** Центроид кластера — реальная площадка борта, и центроиды не
     двигаются: это не Lloyd's, площадки заданы физически. Галсы разбираются от длинных к
     коротким, каждый уходит борту с минимальной суммой «переход туда + накопленная
     загрузка». Галс, который не помещается в бюджет даже в одиночку (туда + галс +
     обратно), уходит в `unassigned_tracks` — это диагностика невыполнимости, не ошибка.
  2. **Тур.** Порядок галсов внутри вылета — ближайший сосед + 2-opt, старт зафиксирован в
     площадке; каждый галс проходится в более близком направлении. На больших кластерах
     2-opt отключается по порогу — эвристика, а не точный решатель.
  3. **Балансировка узкого места.** Пока разрыв между самым и наименее загруженным бортом
     больше порога, последний галс тура самого нагруженного переносится наименее
     нагруженному (если тот его потянет), оба тура перестраиваются.
  4. **Split.** Разбиение тура на вылеты по бюджету — теперь с учётом перехода до галса и
     зарезервированного обратного перехода.

Важное отличие от первой версии: `flight_time_s` вылета включает переходы, а не только
галсы. При кластеризации переходы оцениваются по прямой — считать A* на каждую пару
кандидатов слишком дорого; фактический маршрут в обход зон строится позже, в
`services/plan_service.py`, и налёт пересчитывается по нему.

Тесты: `tests/test_routing_cluster.py` — базовые (нет бортов → всё в `unassigned`,
балансировка при одинаковых площадках, Split по бюджету, слишком длинный галс, валидация
`Vehicle`), переходы в бюджете (дальний галс, обратный переход как причина нового вылета),
своя площадка у каждого борта, качество тура против произвольного порядка, эффект
балансировки.

### `uav_planner.visibility` — обход запрещённых зон на переходах (сеточный A*)

Переходы между галсами и до площадки раньше были прямыми линиями и спокойно пересекали
бесполетные зоны — нарушение ловила только независимая проверка безопасности. Теперь
переход строится в обход.

`find_path(start, goal, obstacles, cell_size_m=20)` → `PathResult(line, detoured, fallback)`:

1. Если прямая свободна — она и возвращается, сетка не строится вовсе. На чистых сценах
   это стоит одну проверку пересечения.
2. Иначе вокруг отрезка и мешающих препятствий строится **локальная** сетка, по ней ищется
   путь A* (8 связей, евклидова эвристика, диагональ `√2`, запрет срезки через угол занятой
   ячейки).
3. Сеточный путь спрямляется жадным «натягиванием нити» по точной геометрии — иначе маршрут
   выглядел бы лесенкой и был бы длиннее необходимого.

Ограничения зафиксированы в докстринге модуля: это сетка, а не граф видимости; при слишком
большой области шаг сетки укрупняется автоматически; ячейки старта и цели всегда считаются
свободными (иначе площадка внутри буфера делала бы задачу неразрешимой); разрешённое
пространство модуль не проверяет — это забота рабочей области.

Если обход не найден (слишком узкий проход для разрешения сетки), возвращается прямая с
признаком `fallback`, и план получает предупреждение: «использована прямая линия,
пересечение проверит модуль „Проверка безопасности“». Молча отдавать пересекающий маршрут
нельзя, а отказываться считать план из-за одного перехода — слишком грубо.

Тесты: `tests/test_visibility_astar.py` — прямая без препятствий и при далёком препятствии,
обход блокирующего препятствия, спрямление (путь не лесенкой), `fallback` при запертой цели,
старт и цель никогда не заблокированы.

### Модуль «Планирование» (Экран 4)

Реализует `docs/trebovania/Планирование.md` (ПЛН.ФТ.2-3, ПЛН.ФТ.5-10) — оркестрирует уже
готовые модули в сквозной, честный, но **упрощённый** расчёт. Известные упрощения первой
версии (документированы также в docstring `services/plan_service.py`):

- **одна модель БВС на план** — смешанный парк в одной задаче остаётся будущей версией. Но
  какая именно модель, решает не эвристика «где больше готовых бортов»: для **каждой**
  подходящей по нагрузке группы «модель + камера» строится полный кандидат плана, и
  побеждает тот, что минимизирует критерий задачи — нормированная взвешенная сумма
  `J = α·J1/J1* + (1−α)·J2/J2*`, где `J1*`/`J2*` — лучшие значения среди посчитанных
  кандидатов (ПЛН.ФТ.2). Платой стало время расчёта: конвейер выполняется столько раз,
  сколько подходящих групп;
- **крейсерская скорость** = паспортный максимум модели минус скорость ветра задачи, без
  учёта направления — консервативная оценка «ветер всегда встречный», до полной модели
  ветра в модуле `motion` (пока не реализован);
- **переходы между галсами и до площадки** обходят бесполетные зоны и высотные препятствия
  через `visibility.find_path`, и налёт вылета пересчитывается по фактическому маршруту
  **до** построения расписания: световой день обязан укладывать настоящую длительность, а
  не приблизительную. При кластеризации (`routing`) переходы всё ещё оцениваются по прямой —
  считать A* на каждую пару кандидатов слишком дорого, — поэтому фактический маршрут обычно
  чуть длиннее оценённого. Порядок галсов внутри вылета оптимизируется под минимальный
  транзит (ближайший сосед + 2-opt), но это эвристика, не точный решатель;
- **площадка старта/посадки** — своя у каждого борта: собственные координаты экземпляра из
  парка, иначе **ближайшая** к области облёта ВПП обстановки (не первая в файле), иначе
  центроид рабочей области. Отдельного шага «выбрать одну площадку на весь план» нет: борта
  летают оттуда, где физически стоят;
- **промежуточное допустимое решение не сохраняется** — поэтому остановка по лимиту
  времени (ПЛН.ФТ.3) фиксируется статусом, но отдать «лучшее из найденного» нечего; это
  появится вместе с решателем OR-Tools, умеющим отдавать incumbent по `time_limit`;
- **LiDAR и геофизическая съёмка** — не поддерживаются (нет камерных профилей), явная
  ошибка 422 с объяснением, а не молчаливый неверный результат.

Независимая проверка результата на нарушения (геозоны, энергия, разведение и т.д.) —
отдельный модуль «Проверка безопасности» (см. ниже), не встроена в сам расчёт.

Модули:
- **`api/schemas/plan.py`** — `PlanSortie` (БВС, время старта/финиша, налёт, дистанция,
  маршрут как GeoJSON `LineString` в WGS-84, отдельно линии галсов),
  `PlanSummary`/`PlanDetail` (версия, J1/J2, модель БВС, число вылетов, предупреждения,
  статус жизненного цикла), `PlanSortiePhase` — этап вылета (взлёт и перелёт до зоны
  задания, галс, переход к следующему галсу, возврат) с временем и длиной. Этапы нужны
  интерфейсу: переходы теперь идут в обход зон и из одной строки расписания не выводятся
  (ИНТ.ФТ.15).
- **`services/plan_service.py`** — `create_plan(task_id, progress=None)`: берёт борта из
  парка задачи, группирует по «модель + камера» (`_group_by_model_camera`) и для каждой
  группы строит кандидата — высота и шаг галсов (`camera`), рабочая область (`geometry`),
  декомпозиция и галсы (`coverage`), кластеризация и разбиение на вылеты (`routing`),
  раскладка вылета на этапы с обходом зон (`_build_sortie_legs` поверх `visibility`),
  пересчёт налёта по фактическому маршруту, расписание (`schedule`), J1/J2. Из кандидатов
  выбирается лучший по критерию задачи (`_pick_best_candidate`). Каждый успешный расчёт —
  новая версия
  (ПЛН.ФТ.4), задача переводится в статус «Рассчитана» (`task_service.mark_calculated`) в
  той же транзакции. Здесь же `confirm_plan()` — подтверждение ЭКС.ФТ.6, см. раздел про
  экспорт. Необязательный `progress` — репортер фонового расчёта; без него поведение
  функции прежнее, что и позволило добавить очередь, не трогая математику.
- **`api/routers/plans.py`** — `POST /api/plans` (form: `task_id`, `wait_s`),
  `GET /api/plans?task_id=` (версии, новые первыми), `GET /api/plans/{id}`, плюс
  `confirm` и `export` (модуль 6). Невыполнимость целиком — `422` с понятной причиной;
  частичная (не все галсы поместились) — `200` с `warnings`, ПЛН.ФТ.10.
- **Попутная правка несогласованности требований**: `Задача.md` (ЗАД.ФТ.11) разрешала
  редактирование только в статусе «Черновик», а `Планирование.md` (ПЛН.ФТ.8) требует
  возможности сменить критерий и пересчитать — по прежней логике это было бы невозможно
  после первого расчёта. Поправил: редактирование запрещено только для «Подтверждена»
  (это уже модуль «Подтверждение и экспорт»); правка параметров задачи возвращает её в
  статус «Черновик» (прежний план остаётся в истории версий).

Экран — в SPA (`web/src/features/plan/`): маршруты на карте (свой цвет на БВС, легенда),
панель с J1/J2, предупреждениями, расписанием и переключателем версий плана, панель
прогресса фонового расчёта с отменой.

Тесты: `tests/test_api_plan.py` — успешный расчёт, перевод задачи в «Рассчитана», маршрут в
ответе `GET /api/plans/{id}`, вторая версия при повторном расчёте, невыполнимость без
готовых бортов / без совместимой нагрузки / для LiDAR, площадка = центроид без ВПП в
обстановке, 404 для неизвестной задачи/плана, влияние ветра на J2; плюс кейсы нового ядра:
переход обходит бесполетную зону, меньшая но более быстрая группа выигрывает по критерию,
площадка выбирается ближайшая а не первая, собственная локация экземпляра важнее ближайшей
ВПП, этапы вылета покрывают весь полёт без разрывов, работа делится между бортами на разных
концах области.

### `uav_planner.safety` — независимая проверка безопасности (семь критериев)

Реализует Таблицу 1 `docs/trebovania/Проверка_безопасности.md` (БЕЗ.ФТ.2) — семь чистых
геометрических/временных проверок результата планирования, формально описанных в
Математическая_модель.md, раздел 15. Модуль не переиспользует внутренний код `routing`/
`coverage`/`plan_service` — только их заявленный результат (маршруты, расписание,
заявленные параметры камеры/скорости/бюджета), поэтому проверка действительно независима:
ошибка в допущениях ядра не повторится незамеченной в проверке.

- **`checks.py`** — `discretize(line, step_m)` (точки вдоль маршрута с заданным шагом,
  включая оба конца); `check_geozones`, `check_allowed_space`, `check_energy`,
  `check_reachability`, `check_coverage`, `check_daylight`, `check_separation` — каждая
  возвращает `CheckResult(name, passed, violations)`, где нарушение — это
  `Violation(message, point)`: не только причина, но и координата «опасного момента» в UTM.
  Показывается до 5 нарушений, дальше — «...и еще N нарушени(й)». Координата нужна, чтобы
  интерфейс поставил маркер на карту (БЕЗ.ФТ.4, ИНТ.ФТ.14): раньше место приходилось
  выводить разбором текста нарушения.
- **`check_energy`** проверяет фактическую длину маршрута целиком, включая переходы. Теперь
  переходы учитываются и при разбиении на вылеты (`routing`), но оцениваются там по прямой,
  а фактический маршрут идёт в обход зон и получается длиннее — поэтому проверка
  по-прежнему способна поймать выход за бюджет, и на сложных сценах ловит.
- **`check_separation`** сравнивает позиции разных БВС (интерполяцией по маршруту с
  постоянной скоростью) в перекрывающиеся по времени интервалы — вскрывает другой реальный
  пробел: распределение по бортам (`routing`) балансирует загрузку, но не координирует
  борта в пространстве и времени, поэтому стартующие с одной площадки могут сблизиться.

Тесты: `tests/test_safety_checks.py` — 22 теста на всех семь функций и `discretize`
(включая найденную и исправленную реальную ошибку на единицу в `discretize`: терялась
последняя точка маршрута при делении длины на шаг нацело).

### Модуль «Проверка безопасности» (Экран 5)

Реализует `docs/trebovania/Проверка_безопасности.md` (БЕЗ.ФТ.1, 3-6). Для независимости
проверка заново разбирает слои обстановки и задачи собственным кодом (не переиспользует
парсинг `plan_service`), но доверяет заявленным физическим параметрам плана (`model_key`,
`camera_key`, `height_m`, `swath_m`, `cruise_speed_mps`, `budget_s` — добавлены в
`PlanDetail` именно для этой независимой проверки) и отдельному полю
`PlanSortie.survey_tracks_geojson` (только галсы, без переходов — нужно для честной
проверки покрытия отдельно от маршрута целиком).

Известные упрощения первой версии (документированы также в docstring
`services/safety_service.py`):

- **автоматический пересчет (БЕЗ.ФТ.3)** — при нарушении вызывает
  `plan_service.create_plan()` повторно, без каких-либо скорректированных параметров
  (адаптация «тип нарушения → корректировка запроса планированию», описанная в концепции
  решения, раздел 4Г, не реализована). Расчётное ядро детерминировано, поэтому на
  неизменной задаче повтор почти всегда воспроизводит то же нарушение — три попытки, как
  правило, расходуются впустую, но ограничение и счётчик попыток соблюдены честно, а не
  имитацией успеха. Предел — `GALS_MAX_AUTO_RECALC`.
- **«Разведение» проверяется на единой высоте** плана (в v1 высота одна на весь план — см.
  упрощения модуля «Планирование»), а не по паре высот двух БВС.

Статус «В процессе автоматического пересчета» (БЕЗ.ФТ.5, жёлтый индикатор) наблюдаем:
цикл БЕЗ.ФТ.3 выполняется в воркере и пишет стадию в строку работы. В синхронном варианте,
где весь цикл проходил внутри одного HTTP-запроса, это состояние снаружи не было видно в
принципе.

Модули:
- **`api/schemas/safety.py`** — `ViolationOut` (стабильный в пределах отчёта идентификатор
  вида `geozones__0`, текст, координаты в WGS-84 и отметка «оператор принял риск»),
  `SafetyCheckOut` (машинное имя, русская подпись из Таблицы 1, признак нарушения, список
  нарушений), `SafetyReport` (итоговый статус, все 7 проверок, счётчик `auto_recalc_count`,
  признак `violations_acknowledged`). Признак выводится из самих нарушений, а не хранится
  колонкой: иначе флаг и список могли бы разойтись.
- **`services/safety_service.py`** — `check_plan(plan_id, progress=None)`: полный цикл
  БЕЗ.ФТ.1+3 (проверка и, при нарушении, до трёх автоматических пересчётов);
  `recheck_plan(plan_id)` — БЕЗ.ФТ.6 «Повторить проверку» (повторный вызов проверки без
  пересчёта); счётчик попыток ключуется по `(task_id, task.version)` — правка задачи
  (новая версия) сбрасывает его автоматически, как и требует БЕЗ.ФТ.3. Подпись вылета
  («БВС · вылет N») к каждому нарушению приписывает оркестратор: чистые проверки знают
  только геометрию, а БЕЗ.ФТ.4 требует назвать борт и вылет — без этого нарушение
  невозможно показать на карте (ИНТ.ФТ.14); координата у нарушения теперь своя, и маркер
  ставится по ней, а не в начало маршрута.
  `set_violation_ignored(report_id, violation_id, ignored)` — **расширение ЭКС.ФТ.2 по
  запросу пользователя**: оператор осознанно принимает риск конкретного нарушения, и если
  приняты все нарушения отчёта, подтверждение плана разблокируется. Область действия —
  конкретный отчёт: новый расчёт и повторная проверка строят отчёт заново, отметки не
  переносятся. Это решение, а не недоработка — принятый риск для одних условий не должен
  молча считаться принятым для другого результата. Отметки хранятся в БД, поэтому
  переживают перезапуск сервиса.
- **`api/routers/safety.py`** — `POST /api/safety-checks` (form: `plan_id`) — полный цикл;
  `POST /api/safety-checks/recheck` — «Повторить проверку»;
  `GET /api/safety-checks/latest?plan_id=`;
  `POST /api/safety-checks/{report_id}/violations/{violation_id}/ignore` (form: `ignored`).

Экран — в SPA (`web/src/features/safety/`): построчный результат всех семи критериев,
итоговый статус-бедж, маркеры нарушений на карте по их координатам, галочка «принимаю риск»
у каждого нарушения, баннер «План пересчитан автоматически».

**Оговорка про принятие риска.** Сводная строка «...и ещё N нарушений» — тоже отдельная
запись со своим идентификатором и своей галочкой. Значит, принимая её, оператор принимает
и те нарушения, которых не видел. Так устроено в ядре; интерфейс это не скрывает, но и не
предупреждает отдельно — вопрос к владельцу требований.

Тесты: `tests/test_api_safety.py` — успешная проверка (все 7 критериев пройдены),
обнаружение **неустранимого** пересечения с бесполетной зоной (маленькую зону расчёт теперь
обходит сам, поэтому для этого кейса в сцене стоит непроходимая «стена»), обход малой зоны
через A* без нарушений, координаты нарушений в WGS-84, стабильные идентификаторы,
частичное и полное принятие нарушений, 404 на неизвестное нарушение и отчёт, исчерпание
лимита автопересчётов
при устойчивом нарушении (с проверкой, что отчёт привязан к последней пересчитанной версии
плана), «Повторить проверку» не создаёт новых версий плана, получение последнего отчёта,
404 без предварительной проверки и для неизвестного плана, отказ «Достижимость площадки»
при отсутствии площадки посадки в обстановке. Дополнительно проверено вручную реальным
HTTP-запросом (обстановка со всеми типами зон и площадок → парк → задача → расчёт →
проверка безопасности с настоящими причинами нарушений).

### `uav_planner.jobs` — очередь и фоновый расчёт (ПЛН.ФТ.3/ФТ.5, БЕЗ.ФТ.3/ФТ.5)

Celery поверх Redis, сервисы `worker` (расчёт) и `beat` (janitor) в compose,
состояние работы — в таблице `plan_jobs`. Устройство и проверенные сценарии
описаны выше, в разделе «Фоновый расчёт»; здесь — что это меняет в математике и
модулях.

Состав пакета: `celery_app.py` (брокер, лимиты времени, расписание janitor'а,
перехват настройки журнала у Celery), `progress.py` (`ProgressReporter`,
`JobCancelled`), `tasks.py` (`run_plan_job`, `run_safety_job`, `escalate_cancel`,
`sweep_stale_jobs`), `control.py` (`revoke`).

Математика не тронута. Оба цикла, которые растут вместе со сценой (по ячейкам
декомпозиции и по бортам), лежат в оркестраторе `plan_service`, а не внутри
чистых модулей, — поэтому честный прогресс по стадиям (загрузка 3 %, подбор
модели 6 %, геометрия съёмки 10 %, рабочая область 20 %, декомпозиция 30 %,
галсы 30→60 %, распределение 75 %, расписание 75→92 %, сохранение 96 %)
получился добавлением необязательного аргумента `progress` в две функции
сервисов. Без него — `plan_service.create_plan(task_id)` и
`safety_service.check_plan(plan_id)` ведут себя ровно как раньше.

Заодно `_pick_model_group` перестал читать парк БВС скрытым глобальным вызовом
в середине расчёта: состав передаётся аргументом, и фоновая работа не зависит
от того, что оператор перезалил парк посреди счёта.

Цикл автоматического пересчёта БЕЗ.ФТ.3 переехал из HTTP-запроса в воркер —
именно это делает наблюдаемым третий статус БЕЗ.ФТ.5 «В процессе
автоматического пересчёта»: внутри одного запроса это состояние снаружи не
видно в принципе. Ограничение в три попытки и привязка отчёта к последней
пересчитанной версии плана при этом не изменились, что подтверждают прежние
тесты модуля без правки ассертов.

Тесты (`tests/test_jobs.py`, 24 шт.): работа создаётся даже при мгновенном
расчёте; ветка 202 и ветка 200 гибридного ожидания; невыполнимость как исход
работы и 422 наружу; идемпотентность по заголовку против новой версии плана без
него; одна активная работа на задачу; отмена на границе стадии; отказ выполнить
отменённую работу, доставленную после перезапуска воркера; видимость прогресса
вне транзакции расчёта; проверка безопасности как работа с
`auto_recalc_count = 3`; исходы «лимит времени» и «внутренний сбой». Отдельно —
janitor: работа без heartbeat добивается, работа со свежим heartbeat и работа
«В очереди» не трогаются, а чтение статуса больше ничего не чинит само.

### Модуль «Подтверждение и экспорт» (Экран 6, ЭКС.ФТ.1-9)

Жизненный цикл версии плана: **Черновик → Проверен → Подтверждён → Выгружен**
(ЭКС.ФТ.5). Каждый переход — условный `UPDATE ... WHERE status = :ожидаемый`, а
не «прочитать и записать»: ЭКС.ФТ.9 требует, чтобы при одновременном
подтверждении выиграл первый, а второй получил `409` с актуальным статусом и
сообщением «План уже подтверждён пользователем (ФИО)».

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/plans/{id}/confirm` | подтверждение (ЭКС.ФТ.6), form `confirmed_by`; `422` — предусловие ЭКС.ФТ.2 не выполнено, `409` — уже подтверждён |
| `GET` | `/api/plans/{id}/export/kml/{uav_id}` | KML по одному БВС (ЭКС.ФТ.7-8) |
| `GET` | `/api/plans/{id}/export/geojson/{uav_id}` | GeoJSON по одному БВС |
| `GET` | `/api/plans/{id}/export/zip` | архив: KML и GeoJSON по каждому БВС (ЭКС.ФТ.7) |

Предусловие ЭКС.ФТ.2 проверяется по последнему отчёту: проверка выполнена,
относится **к этой же версии плана** и не содержит нарушений. Вторая часть
важнее, чем кажется: после автопересчёта БЕЗ.ФТ.3 отчёт относится к новой
версии, и подтвердить непроверенную версию нельзя.

**Подтверждение вопреки нарушениям** (расширение ЭКС.ФТ.2 по запросу
пользователя). Если оператор отметил принятым каждое нарушение последнего
отчёта, требование «без нарушений» снимается. Остальные два остаются:
проверка обязана быть выполнена и относиться именно к этой версии — иначе
принимался бы риск, которого никто не измерял. Такой план получает отметку
`confirmed_with_overrides`, и она видна в карточке: по журналу должно быть
понятно, что план не проходил проверку.

**Кто именно подтвердил.** Аутентификации по ТЗ нет (ответы экспертов, п. 21).
ФИО приходит полем формы `confirmed_by` — это контракт модуля; если поле не
прислали, берётся заголовок `X-User-Name`, которым подписаны правки задач
(ЗАД.ФТ.12), и только потом «Оператор». Терять подпись из-за пустого поля
незачем.
ФИО кириллические, а значение заголовка — октеты, которые каждый стек
декодирует по-своему, поэтому принимаются оба встречающихся варианта:
процентное кодирование UTF-8 (то, что должен слать корректный клиент) и сырые
UTF-8-байты, как их кладёт браузер, — последние доезжают «кракозябрами» после
latin-1 и восстанавливаются обратно.

**Файлы не хранятся.** KML и GeoJSON — чистая функция от плана, а план после
подтверждения неизменяем (ЭКС.ФТ.3), поэтому повторная генерация даёт то же
самое; архив собирается без штампов времени и совпадает байт в байт (проверено
на живом стенде до и после перезапуска контейнеров). В `export_artifacts`
пишется только факт выгрузки — он нужен статусу «Выгружен» и разбору «что
именно скачали и когда».

Имена файлов — `{инвентарный номер}_v{версия}.kml` и `plan_v{версия}_export.zip`.
Инвентарные номера бывают кириллическими, поэтому `Content-Disposition`
отдаётся по RFC 5987 (`filename*=UTF-8''…`) с запасным ASCII-вариантом — иначе
браузер имя портит.

#### Состав экспорта

KML (ЭКС.ФТ.8): `Document → Folder(БВС) → Folder(вылет)`; в вылете — `TimeSpan`
на весь вылет, Placemark «Маршрут» (`LineString`,
`altitudeMode=relativeToGround`), Placemark «Галсы» (`MultiGeometry`) и по
Placemark на ключевую точку с `TimeStamp`; этап, высота и скорость — в
`ExtendedData`. Время — ISO 8601 UTC с суффиксом `Z`, координаты — WGS-84
`lon,lat,alt` (ЭКС.ФТ.4).

Точную таблицу свойств GeoJSON ТЗ выносит в документ «Методы, раздел 7»,
которого у нас нет, — зафиксирован свой набор (ответы экспертов, п. 22):

Вид объекта лежит в свойстве `type`; все геометрии трёхмерные, третья
координата — высота съёмки плана (высотного профиля модель не ведёт), у зоны
покрытия — 0, это проекция на землю.

| Объект | Геометрия | Свойства |
|---|---|---|
| Вылет | LineString | `uav_id`, `sortie_index`, `takeoff_site`, `landing_site`, `start_utc`, `end_utc`, `flight_time_s`, `distance_m`, `speed_mps`, `altitude_m` |
| Ключевая точка | Point `[lon, lat, alt]` | `sequence`, `label`, `kind`, `utc` |
| Галсы вылета | MultiLineString | `swath_m`, `altitude_m` |
| Зона покрытия | Polygon / MultiPolygon | `swath_m` |

Ключевые точки восстанавливаются из этапов вылета (`PlanSortiePhase`)
интерполяцией вдоль фактического маршрута: весь вылет летится на одной
крейсерской скорости, поэтому расстояние и время связаны линейно и
интерполяция по длине физически точна.

Плюс `properties` на всей коллекции: идентификаторы плана и задачи, версия,
БВС, модель, критерий и `crs`. KML пишет это в `<name>`, и выгруженный
GeoJSON тоже обязан сам называть план, из которого получен.

**Чего в ядре v1 нет и как это восполнено честно.** Расчёт сохраняет на вылет
только линию маршрута, линии галсов и время старта/посадки — списка ключевых
точек с этапом и временем прохода в нём пока не существует. Поэтому точки
выводятся из самого маршрута: вершина линии; этап — «Взлёт» для первой,
«Посадка» для последней, «Съёмка» если вершина совпадает с вершиной галса,
иначе «Перелёт»; время прохода — линейная интерполяция между стартом и
посадкой по накопленной метрической длине, что соответствует принятой в v1
постоянной крейсерской скорости. Разгон, развороты и ожидание на земле
появятся вместе с модулем `motion`. По той же причине линия маршрута в KML
идёт на одной высоте съёмки, а нулевая высота проставлена только точкам взлёта
и посадки. Зона покрытия — буфер галсов на полполосы захвата, то же понятие,
которым пользуется проверка покрытия.

Тесты (`tests/test_api_export.py`, 21 шт.): статусы на каждом переходе;
повторная проверка не откатывает цикл назад; подтверждение без проверки и с
нарушениями отклоняется; второй подтверждающий получает 409 с именем первого;
ФИО из заголовка в обоих кодировках; экспорт до подтверждения — 409; структура
KML разбирается как XML и проверяется по узлам (папки, TimeSpan, TimeStamp,
`altitudeMode`, ExtendedData); координаты KML — WGS-84 `lon,lat,alt`; в GeoJSON
присутствуют все четыре вида объектов; времена ключевых точек монотонны и
совпадают со стартом и посадкой; неизвестный БВС — 404; архив содержит оба
формата и разбирается; кириллическое имя файла в RFC 5987; повторная выгрузка
байт в байт и журналируется.

### `web/` — SPA (React + TypeScript + Vite за nginx)

Единственный фронтенд продукта. Экраны 1–5 перенесены из прежнего
одностраничного `static/index.html` визуально «пиксель в пиксель», экран 6
«Подтверждение и экспорт» и панель прогресса фонового расчёта — новые. Перенос
вёлся по чек-листу [`web/PARITY.md`](web/PARITY.md): он написан **до** начала
работы, все 62 пункта закрыты и проверены в браузере на поднятом стенде, а
удаление `static/index.html` вошло в тот же коммит, что и закрытие последнего
пункта. Миграция фронтенда без запланированного удаления не заканчивается
никогда.

Решения, которые стоит знать, прежде чем править:

- **Одна карта Leaflet на всё приложение.** Её создаёт `AppShell` — layout-route
  над всеми экранами. Если бы карту создавал экран, каждый переход пересоздавал
  бы `L.Map` вместе с панелями и видом, и оператор терял бы масштаб на каждом
  шаге. Экраны объявляют свой шаг через `useStep`, рисуют панель и легенду
  порталом в слоты каркаса, а слои карты добавляют обычными компонентами,
  которые рендерят `null` и владеют своей `L.LayerGroup`.
- **Сырой Leaflet, а не react-leaflet.** Слои живут вне React-дерева:
  `LayerGroup` создаётся один раз, содержимое перестраивается только при смене
  идентичности данных. Перерисовка боковой панели не должна пересоздавать
  полигоны, а на плане с тысячами сегментов это заметно. Маршруты рисуются SVG
  (нужны тултипы), галсы — canvas.
- **Подгонка вида только при смене `boundsKey`.** В первой версии `fitBounds`
  звался на каждый рендер и вырывал карту из-под пользователя.
- **Оффлайн по умолчанию.** Шрифты (Onest, PT Mono) и Leaflet бандлятся из npm,
  подложки карты нет вовсе: пустой фон `--paper` плюс слои обстановки. Так
  интерфейс сразу работает в закрытом контуре; `VITE_TILE_URL` на сборке
  включает OSM, кеширующий прокси или предзалитую пирамиду в томе.
- **Типы генерируются, клиент пишется руками.** `scripts/dump_openapi.py`
  снимает схему с объекта приложения, `openapi-typescript` делает из неё типы.
  Генераторы клиента здесь не годятся: их multipart-сериализаторы ломаются на
  `float | None = Form(None)` и на `date`/`time`.
- **Пустое поле формы — ключ не отправляется вовсе.** `Form(None)` в FastAPI
  разбирает пустую строку как значение и отвечает 422; первая версия делала это
  правильно, и регрессировать нельзя. Область облёта всегда уходит файлом, в том
  числе при правке без её изменения, — бэкенд требует `area_file` и на PUT.
- **Опрос работы не замирает в фоновой вкладке** (`refetchIntervalInBackground`).
  По умолчанию TanStack Query замораживает интервал в неактивной вкладке —
  именно так с получасовым расчётом и работают, и индикатор застывал бы на том
  проценте, который оператор видел перед переключением. Найдено вживую.

Проверено в браузере на поднятом стеке: загрузка обстановки и панель ошибок
(сцена `examples/scene_with_errors.geojson` — четыре ошибки, невалидные объекты
красным пунктиром, переход дальше заблокирован); рисование области кликами по
карте и создание задачи; расчёт в обоих режимах — синхронный ответ 200 и
режим прода `wait_s=0` с панелью прогресса, переподключением после F5 и
отменой; проверка безопасности как фоновая работа с наблюдаемым статусом
«В процессе автоматического пересчёта (1 из 3)»; баннер «План пересчитан
автоматически, показана версия 4» с переходом на проверенную версию; маркеры
нарушений на карте; переключатель версий плана; подтверждение с именем
оператора из `X-User-Name` и кнопки экспорта.

## В работе / далее

Со стороны математики: настоящий граф видимости вместо сеточного A* (сейчас узкие проходы
могут оказаться уже разрешения сетки, и тогда переход откатывается на прямую с
предупреждением), полная кинематика с ветром (`motion`, сейчас — только константная
крейсерская скорость минус ветер, без учёта направления), список ключевых точек с этапом и
временем прохода прямо из расчёта (сейчас экспорт выводит их интерполяцией по маршруту),
фильтрация кандидатов по высоте/ветру/достижимости ВПП (`fleet.eligible_uavs`) и решатель
OR-Tools Routing вместо эвристик — с ним же появится «лучшее найденное решение» при
остановке по лимиту времени (ПЛН.ФТ.3) и смешанный парк в одной задаче.

Отдельно стоит померить и ускорить сам перебор кандидатов: сейчас для каждой группы
«модель + камера» считается полный конвейер, включая рабочую область и галсы, хотя часть
работы между кандидатами общая (различается только высота съёмки). На сцене Екатеринбурга
это 43 секунды, и с ростом парка время растёт линейно по числу групп.

Со стороны обвязки осталась одна известная вещь. Тело фоновой работы идёт **одной
транзакцией на весь расчёт** — так вставка плана и `mark_calculated` не могут разъехаться
(прогресс при этом пишется своими короткими транзакциями и виден сразу). На сценах, где
расчёт идёт минуты, открытый всё это время снимок будет мешать `VACUUM`. Чистое
разделение «прочитать вход → посчитать без транзакции → записать результат» возможно: в
`create_plan` середина конвейера к БД не обращается вовсе. Но у проверки безопасности цикл
автопересчёта БЕЗ.ФТ.3 чередует запись (счётчик попыток, новые версии плана) с расчётом, и
разделить только план значило бы оставить проблему там, где работа как раз самая длинная —
до четырёх проверок и трёх пересчётов подряд. Поэтому разделение отложено до того же
шага, что и OR-Tools. Оговорка: после слияния с новым ядром конвейер укладывается уже не в
секунды, а в десятки секунд, и на больших сценах этот пункт стал ближе,
а после появления решателя разделять придётся оба оркестратора сразу и по общей схеме.

Из обвязки не сделано и известно: **CI отсутствует** — прогон тестов, `npm run
typecheck`/`build` и проверка рассинхрона `openapi.json` запускаются вручную;
из запланированных compose-профилей есть только базовый и dev, а
`docker-compose.test.yml` (PostGIS на tmpfs плюс сервис `tests`, чтобы прогон
не требовал ничего на хосте) и `docker-compose.prod.yml` (без bind-mount и
открытых портов БД, лимиты ресурсов) не написаны.

Актуальный статус — на канбане.
