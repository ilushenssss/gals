# uav-planner

Сервис планирования и распределения беспилотных авиационных работ — кейс **Галс** (2026).

Постановка задачи, ответы экспертов, концепция решения, обзор методов и план реализации —
в [`docs/realization`](../docs/realization); ход работы по карточкам — на канбан-доске
[`docs/code/uav_planner_kanban.html`](../docs/code/uav_planner_kanban.html). Этот файл —
журнал того, что уже реализовано в коде, и как это запустить.

## Статус проекта на сегодня

- **Документация** (`docs/realization`): изучены ТЗ и ответы экспертов; написаны концепция
  решения, обзор методов (с обоснованием по статье Wang et al., 2025) и план реализации
  (роли, график 16–29.09, тест-матрица T1–T14, риски).
- **Открытые неточности ТЗ зафиксированы** как принятые допущения (раздел «Открытые
  неточности» в [`uav_planner_plan.html`](../docs/realization/uav_planner_plan.html#process)) —
  без них к реализации не приступаем, чтобы не блокироваться на ответах экспертов.
- **Канбан-доска** (`docs/code/uav_planner_kanban.html`) — задачи по обеим ролям (математика,
  интерфейсы) разнесены по этапам 0–4, с отражением текущего статуса выполнения.
- **Код** (`main/`, этот пакет) — сквозной расчёт от загрузки обстановки до плана с
  маршрутами и метриками работает от начала до конца, вместе с независимой проверкой
  безопасности результата (Экраны 1–5 интерфейса): «Проекция и рабочая область», «Высота
  съёмки H», «Декомпозиция на ячейки», обход бесполетных зон/препятствий на переходах
  сеточным A* (`uav_planner.visibility`), распределение и разбиение на вылеты (`routing`),
  расписание со световым днём (`schedule.timeline`), энергобюджет (`fleet.energy`),
  «Проверка безопасности» (семь критериев из `uav_planner.safety`) и «Подтверждение и
  экспорт» (статус плана, ручное подтверждение, экспорт в KML/GeoJSON по каждому БВС) —
  всё реализовано и покрыто тестами, с честно документированными упрощениями первой версии
  (одна модель БВС на план, без ветра по направлению, обход препятствий на перелётах
  сеточный, а не по графу видимости, автопересчёт при нарушении без адаптации параметров,
  нет модели пользователей — «ФИО» подтверждающего вводится свободным текстом). Плюс модуль
  «Парк БВС» и меню «Парк / История / Создать задачу» (см. раздел ниже). FastAPI + Leaflet,
  сборка через Docker — подробности в разделе «Реализовано» ниже.
- **Продуктовый стек** — перенесён из ветки `merge-core-into-wrapper` (см. «Архитектура и
  развёртывание» ниже): PostgreSQL/PostGIS вместо хранения в памяти процесса, фоновый расчёт
  через Celery/Redis с прогрессом и отменой (закрывает пункт «фоновый расчёт — будущая
  версия» выше), структурное логирование, Alembic-миграции, docker-compose на 6 сервисов.
  Фронтенд остался тем же vanilla-JS интерфейсом — React SPA этой ветки не перенесена
  (решение пользователя): один интерфейс вместо двух дублирующих.
- **Требования** (`docs/trebovania`) — функциональные требования по модулям в
  формате техзадания, отдельные документы по интерфейсу (`Интерфейс.md`) и
  полной математической модели алгоритма (`Математическая_модель.md`).

## Архитектура и развёртывание

Продуктовый стек перенесён из ветки `merge-core-into-wrapper` в `main` целиком, кроме
React-SPA (`web/`) — фронтенд остался тем же vanilla-JS файлом `static/index.html`, что и был,
раздаётся тем же процессом `api`, как раньше. Контракты модулей `environment`/`fleet`/`task`/
`safety`/`export` между ветками совпадали почти field-for-field (независимая эволюция одного
и того же функционала), поэтому большая часть фронтенда перенесена без изменений; два места,
где поведение бэкенда стало другим, — гибридный синхронный/фоновый ответ `POST /api/plans` и
`POST /api/safety-checks`, и переопределённая семантика `PlanDetail.status == "Проверен"` —
описаны в соответствующих разделах «Реализовано» выше.

- **Хранилище** — PostgreSQL 16 + PostGIS через SQLAlchemy (`db/`, `models/`) и слой
  репозиториев (`repositories/`) вместо словарей в памяти процесса. Схема — Alembic-миграции
  (`migrations/`, 8 ревизий).
- **API** — слоистый вместо плоских файлов: `api/schemas/` (Pydantic-контракты, было
  `*_models.py`), `api/routers/` (маршруты, было `*_routes.py`), `services/` (бизнес-логика,
  было `api/*_service.py`). Сессия БД — на один HTTP-запрос (`api/middleware.py`).
- **Фоновый расчёт** — Celery + Redis (`jobs/`): расчёт плана и цикл проверки безопасности
  всегда уходят в очередь, но `POST /api/plans`/`POST /api/safety-checks` до
  `GALS_PLAN_SYNC_WAIT_SECONDS` (30 с в dev) ждут завершения и отдают прежний синхронный `200`
  — быстрые тестовые сцены не замечают разницы. Не успел — `202` с объектом работы, фронтенд
  опрашивает `GET /api/plan-jobs/{id}` и может отменить (`POST /api/plan-jobs/{id}/cancel`);
  переподключается к идущей работе и после перезагрузки вкладки.
- **Логирование** — структурное (`logging_setup.py`), с `request_id`/`job_id`/`task_id` в
  контексте (`log_context`).
- **Конфигурация** — `config.py` (pydantic-settings, переменные окружения с префиксом
  `GALS_`, см. `.env.example`).
- **Развёртывание** — `docker-compose.yml`: `db` (PostGIS), `redis`, одноразовый `migrate`
  (`alembic upgrade head`), `api` (тот же процесс отдаёт API и статический фронтенд, как и
  раньше — порт `API_PORT`, по умолчанию 8000), `worker` (фоновый расчёт), `beat` (janitor,
  добивает осиротевшие работы). Сервиса `web`/nginx нет — SPA не перенесена.

## Структура

```
main/
  pyproject.toml
  docker-compose.yml
  alembic.ini
  migrations/            # Alembic-ревизии схемы PostgreSQL/PostGIS
  src/uav_planner/
    geometry/             # проекции, рабочая область, буферы (см. ниже)
    db/                   # SQLAlchemy engine/session, геометрия PostGIS
    models/               # ORM-модели
    repositories/         # доступ к БД по модулям
    services/             # бизнес-логика по модулям (было api/*_service.py)
    jobs/                 # Celery: фоновый расчет плана/проверки, janitor
    api/
      schemas/             # Pydantic-контракты (было api/*_models.py)
      routers/              # HTTP-маршруты (было api/*_routes.py)
      static/               # vanilla-JS фронтенд (index.html)
    config.py              # настройки (pydantic-settings, GALS_*)
    logging_setup.py       # структурное логирование
  tests/
```

## Запуск

```bash
cd main
python -m venv .venv
.venv/Scripts/python.exe -m pip install -e ".[dev]"   # Windows
# source .venv/bin/activate && pip install -e ".[dev]"  # Linux/macOS
.venv/Scripts/python.exe -m pytest -v
```

Хранилище — PostgreSQL/PostGIS (после переноса продуктового стека), поэтому тесты, помеченные
`db` (большинство `test_api_*.py`), нужен настоящий Postgres: либо `GALS_TEST_DATABASE_URL`
(например, `db`-сервис из `docker compose`, поднятый отдельно — `docker compose up -d db` —
с отдельной базой `gals_test`, не рабочей `gals`), либо testcontainers (зависимость уже в
`dev`-экстре, поднимает контейнер сам, нужен только Docker). Без БД тесты с меткой `db`
пропускаются, тесты чистой математики идут как обычно.

### Веб-интерфейс (первая версия)

Проще всего — весь стек через Docker (см. ниже). Для запуска без контейнера API нужен
настоящий Postgres (`GALS_DATABASE_URL`) и накатанные миграции:

```bash
GALS_DATABASE_URL=postgresql+psycopg://gals:gals@127.0.0.1:55432/gals \
  .venv/Scripts/python.exe -m alembic upgrade head
GALS_DATABASE_URL=postgresql+psycopg://gals:gals@127.0.0.1:55432/gals \
  .venv/Scripts/python.exe -m uvicorn uav_planner.api.app:app --reload
```

Открыть `http://127.0.0.1:8000/` — Экран 1 (пустая карта + кнопка «Загрузить данные») и Экран 2
(зоны обстановки на карте после загрузки) документа [`Интерфейс.md`](../docs/trebovania/Интерфейс.md).
Формат файла обстановки — GeoJSON FeatureCollection со свойством `layer`
(`launch_site`, `airspace`, `no_fly`, `obstacle`, `reserve_site`), см.
`uav_planner.api.schemas.environment`.

Логотип (`main/img/logo.png`) — светлый серо-голубой, поэтому в шапке лежит на плашке
фиксированного тёмного цвета (`--brand-chip`, не меняется со сменой темы) — иначе на светлой
теме он терялся бы на практически неотличимом по цвету фоне `#stepper-bar`. Уменьшенная копия
для шапки (128×128, ~10 КБ вместо 427 КБ оригинала) лежит в `static/img/logo.png`; проверено
сборкой Docker, что вложенная папка `static/img/` попадает в неinteractive `pip install .`
(`package-data` уже включал `static/**/*`).

Тестовые сцены для загрузки — `main/examples/`:

- `scene_ekaterinburg_complex.geojson` + `fleet_ekaterinburg_complex.json` — сложная сцена в

  соседняя башня 209 м, плюс труба ТЭЦ 250 м, радиомачты 100–220 м, строительный кран,
  элеватор, пилон моста, опора ЛЭП, колокольня — от 55 до 250 м, разбросаны по всему району,

  программно (валидность полигонов, точки вне БПЗ и внутри разрешённого пространства) —
  загружаются и считают план без ошибок, проверено реальным HTTP-запросом «в конец» (обстановка

```bash
cd main
docker compose up --build
```

Открыть `http://127.0.0.1:8000/` — тот же интерфейс, без установки Python/зависимостей на
хост. `Dockerfile` собирает `uav-planner` обычным (не editable) `pip install .` — поэтому
статика фронтенда объявлена как `package-data` в `pyproject.toml` (`uav_planner.api` →
`static/*`), иначе non-editable сборка потеряла бы `static/index.html`. `docker-compose.yml`
поднимает 6 сервисов: `db` (PostGIS), `redis`, одноразовый `migrate` (`alembic upgrade head`),
`api` (тот же процесс отдает API и статический фронтенд, как и раньше), `worker` (фоновый
расчет плана и проверки безопасности, Celery) и `beat` (janitor, добивает осиротевшие работы);
`docker-compose.override.yml` (dev, подхватывается автоматически) публикует порт БД наружу и
монтирует код внутрь `api`/`worker`/`beat` для `--reload`/`restart` без пересборки образа —
это требует `PYTHONPATH=/app/src`, иначе не работает вовсе (реально найдено при отладке KML-
загрузки, см. ниже): `Dockerfile` ставит `uav-planner` обычным (не editable) `pip install .`,
то есть в образе пакет лежит копией в site-packages; без `PYTHONPATH` `import uav_planner`
резолвится именно в эту копию, `--reload` честно перезапускается на правку файла в
смонтированном `./src`, но перезапускается на ту же самую старую копию — правка никогда не
долетает до работающего кода, при этом никакой ошибки нет, только тихо неизменное поведение.
Сервиса `web`/nginx (React SPA) нет — при переносе продуктового стека она сознательно не
перенесена, фронтенд остался тем же vanilla-JS файлом. Проверено: реальная
сборка образа и запуск всего стека, `curl` до `/`, `/api/health`, `/openapi.json`; полный
сквозной цикл через настоящий Celery-воркер (не eager-режим) — обстановка → парк → проверка
совместимости 150 км (честный `400`) → задача → расчет плана на сложной екатеринбургской
сцене, ушедший в фоновую работу (`202`, ~93 с реального времени по логам воркера — сцена не
укладывается в 30-секундное окно синхронного ответа) → проверка безопасности с автоматическим
пересчетом → «История» отдает обе созданные задачи.

## Реализовано

> Раздел ниже писался по мере реализации модулей и местами всё ещё называет старые пути
> файлов и «словарь в памяти процесса» как хранилище — это верно для бизнес-логики каждого
> модуля (она не менялась), но не для физического хранения и раскладки файлов. После переноса
> продуктового стека из ветки `merge-core-into-wrapper` (см. новый раздел «Архитектура и
> развёртывание» ниже) хранилище — PostgreSQL/PostGIS через `repositories/`, а плоские файлы
> `api/*_models.py`/`*_routes.py`/`*_service.py` разложены на `api/schemas/`, `api/routers/`,
> `services/`. Там, где это меняет наблюдаемое поведение (не только раскладку файлов), это
> отмечено отдельно по месту.

### `uav_planner.geometry` — проекция и рабочая область

Карточка канбана «Математика → Проекция и рабочая область» (этап 0).

#### `projection.py`

- **`utm_crs_for(lon, lat) -> CRS`** — считает номер зоны UTM (`int((lon+180)//6)+1`) и
  возвращает CRS `WGS 84 / UTM zone N` или `...S` (EPSG 326xx/327xx) в зависимости от
  знака широты. Чистая функция, без сети.
- **`Projector`** — держит пару трансформаций `pyproj.Transformer` (WGS-84 → UTM и обратно)
  для одной, уже выбранной, зоны:
  - `Projector.for_point(lon, lat)` — фабрика: строит проекцию для зоны, в которую
    попадает точка.
  - `Projector.for_geometry(geom)` — то же самое, но зона выбирается по центроиду
    геометрии (полигона области, парка ВПП и т. п.) — так весь расчет сцены идет в одной
    системе координат.
  - `.to_utm(geom)` / `.to_wgs84(geom)` — прогоняют shapely-геометрию (точку, полигон,
    мультиполигон — что угодно) через `shapely.ops.transform` с сохранением порядка осей
    `(x, y)` = `(lon, lat)` / `(easting, northing)`, т. е. без путаницы lat/lon, характерной
    для proj4 по умолчанию.

#### `area.py`

- **`HeightRange(h_min, h_max)`** — диапазон высот, датакласс с проверкой `h_min <= h_max`
  в `__post_init__`; метод `.contains(h)` — попадает ли высота в диапазон.
- **`TimeWindow(start, end)`** — интервал действия зоны (даты/время); тот же принцип:
  проверка порядка в `__post_init__`, метод `.contains(when)`.
- **`AllowedZone(id, polygon, height, active_windows=None)`** — зона разрешенного
  воздушного пространства: полигон + диапазон высот + (опционально) список `TimeWindow`.
  `.is_active_at(when=None)` — активна ли зона в момент `when`; без интервалов или без
  переданного `when` зона считается активной всегда (консервативно).
- **`NoFlyZone(id, polygon, safety_buffer_m=0.0, active_windows=None)`** — бесполетная
  зона. `.footprint()` — контур зоны, раздутый на `safety_buffer_m` (если буфер задан) —
  именно эта раздутая форма вычитается из рабочей области, а не исходный полигон.
  `.is_active_at()` — как у `AllowedZone`.
- **`Obstacle(id, polygon, height, safety_buffer_m=0.0)`** — высотное препятствие,
  «призма» полигон + `[h_min, h_max]`. `.footprint()` — контур с буфером (как у
  `NoFlyZone`). `.is_hole_at(survey_height_m, margin_m=0.0)` — булев признак: становится
  ли препятствие дырой в рабочей области при заданной съемочной высоте H — истина, если
  `h_max + margin >= survey_height_m` (объект не ниже уровня съемки, даже с запасом).
- **`validate_polygon(geom) -> geom`** — проверяет, что геометрия не пустая и
  `geom.is_valid`; на невалидной геометрии (в т. ч. самопересекающийся контур — по
  определению OGC/shapely это уже невалидность) бросает `GeometryError` с текстом причины
  из `shapely.validation.explain_validity`. Возвращает ту же геометрию — удобно для
  `assert validate_polygon(g) is g` и для использования в цепочке вызовов.
- **`safe_simplify(polygon, tolerance_m, safety_buffer_m) -> geom`** — упрощение контура
  алгоритмом Дугласа — Пекера (`shapely.simplify(..., preserve_topology=True)`), но
  сначала проверяет `tolerance_m < safety_buffer_m` и бросает `ValueError`, если это не
  так — иначе упрощенный полигон может выйти за пределы буфера безопасности зоны.
- **`compute_working_area(survey_area, allowed_zones, no_fly_zones, obstacles, survey_height_m, obstacle_margin_m=0.0, when=None) -> geom`**
  — основная функция модуля, считает рабочую область по формуле
  `(Область ∩ Разрешенное) − БПЗ − препятствия выше H`:
  1. проверяет `survey_area` через `validate_polygon`;
  2. если заданы `allowed_zones` — оставляет только те, что покрывают `survey_height_m`
     по высоте и активны в момент `when`, объединяет их (`unary_union`) и пересекает с
     областью; если ни одна зона не подошла — бросает `GeometryError` (высота съемки не
     покрыта разрешенным пространством);
  3. вычитает `footprint()` всех активных `NoFlyZone`;
  4. вычитает `footprint()` всех `Obstacle`, для которых `is_hole_at(H)` истинно.
  Вычитание (внутренняя `_subtract_footprints`) строит `STRtree` по зонам-кандидатам и
  запрашивает только реально пересекающие рабочую область (`predicate="intersects"`) —
  не гоняет `.difference()` по зонам сцены, которые область не касаются.

#### `errors.py`

- **`GeometryError(ValueError)`** — единственное исключение модуля: невалидная/пустая
  геометрия, самопересечение, высота съемки не покрыта разрешенным пространством. Отдельный
  тип, чтобы вызывающий код (API, проверка безопасности) отличал ошибку геометрии от прочих
  `ValueError`.

Все геометрии внутри модуля — в проекции UTM (метры); вход/выход сервиса — WGS-84
(перевод — через `Projector`). Принятые допущения по неточностям ТЗ — в
[`uav_planner_plan.html#process`](../docs/realization/uav_planner_plan.html#process).

Тесты: `tests/test_projection.py`, `tests/test_area.py` — 18 тестов, покрывают выбор зоны UTM
(север/юг, границы), обратимость проекции, сохранение площади, вычитание БПЗ, дыры от
препятствий, интервалы действия по времени, защиту `safe_simplify`.

### `uav_planner.camera` — высота съемки H и шаг галсов d

Карточка канбана «Математика → Высота съемки H и шаг галсов d» (этап 0).

- **`specs.py`** — справочник камер `CAMERA_SPECS` (фокусное расстояние, размер матрицы,
  разрешение кадра) и справочник моделей БВС `UAV_MODELS` (высотный диапазон
  `UavHeightLimits`, совместимые камеры) для трёх моделей Геоскан (201, Gemini, 801).
  Функции `is_height_allowed(uav_model_key, height_m)` и
  `is_camera_compatible(uav_model_key, camera_key)` — проверки допустимости связки.
  Для Sony RX1RM2 и PF1B параметры паспортные; для Pollux, тепловизора 640×512 и
  RGB-камеры 12 Мп (801) — оценка по типовым сенсорам такого класса, помечена
  `verified=False` (см. допущение в [плане реализации](../docs/realization/uav_planner_plan.html#process)).
- **`optics.py`** — формулы: `survey_height(camera, gsd_cm)` — высота по целевому GSD
  (`H = GSD·f·N_w/s_w`); `swath_width()`/`footprint_length()` — ширина полосы захвата и
  длина кадра вдоль трека на заданной высоте; `track_spacing()`/`trigger_spacing()` — шаг
  между галсами и шаг срабатывания камеры при заданном перекрытии (с проверкой, что
  перекрытие в `[0, 1)`). `plan_survey_geometry(uav_model_key, camera_key, gsd_cm, ...)` —
  собирает всё в `SurveyGeometry`, предварительно проверив совместимость камеры с моделью
  и попадание расчётной H в высотный диапазон модели; иначе — `CameraError`.
- **`errors.py`** — `CameraError(ValueError)`.

Тесты: `tests/test_camera.py` — 13 тестов; для RX1RM2 и PF1B расчётные H/B/d сверены с
контрольной таблицей концепции (раздел 3) с допуском 5% и совпадают; для Pollux — тот же
расчёт с допуском 20% (нет паспортных данных сенсора); плюс проверки границ высотных
диапазонов моделей, совместимости камер и отказов `plan_survey_geometry`.

### `uav_planner.coverage` — декомпозиция области на ячейки и галсы

Карточка канбана «Математика → Декомпозиция области на ячейки» (этап 0).

- **`direction.py`** — `best_sweep_direction(polygon, wind_bearing_deg=None, wind_penalty_weight=0.15)`:
  минимальная ширина по выпуклой оболочке (Huang, 2001) — перебираются направления
  только вдоль сторон оболочки (вращающиеся калиперы), так как для выпуклой фигуры
  оптимум доказанно достигается на одной из них. С заданным `wind_bearing_deg`
  штрафует направления с сильной поперечной составляющей ветра:
  `cost = width · (1 + wind_penalty_weight · crosswind_fraction)`. `crosswind_fraction()` —
  доля ветра поперек галсов (0 — вдоль, 1 — строго поперек).
- **`cells.py`** — `Cell(polygon, direction_deg)` и `boustrophedon_cells(area, wind_bearing_deg=None, min_cell_area_m2=1.0)`.
  Режет рабочую область горизонтальными полосами (в системе координат, повёрнутой так,
  что общее для всей области направление слайсинга совпадает с осью X) по критическим
  Y — координатам вершин полигона и его дыр; полосы с одинаковой связностью объединяет
  в одну ячейку (без явной классификации событий IN/OUT/split/merge, но с тем же
  результатом, что у классической boustrophedon cellular decomposition Choset & Pignon,
  1997). Каждая полученная ячейка не содержит внутренних дыр; направление галсов внутри
  неё выбирается заново — по минимальной ширине именно этой ячейки, а не всей области.
  `min_cell_area_m2` отсекает численный мусор — тонкие сколы на вершинах. Мультиполигон
  обрабатывается по частям (они физически не связаны).
- **`tracks.py`** — `generate_tracks(cell, spacing_m)`: параллельные галсы с шагом
  `spacing_m` вдоль `cell.direction_deg`, каждый обрезан по фактической границе ячейки
  через пересечение (не по прямоугольной оценке) — если ячейка не идеально выпукла в
  выбранном направлении, для одной позиции вернётся несколько отрезков вместо одного;
  область всё равно покрыта полностью и без выхода за её пределы, это не ошибка, а
  корректный случай. `split_long_track(track, max_len_m)` — режет галс на равные части
  не длиннее `max_len_m` (нарезка на вылеты — позже, в `routing`, но лимит длины участка
  общий).
- **`errors.py`** — `CoverageError(ValueError)`.

Тесты: `tests/test_direction.py`, `tests/test_cells.py`, `tests/test_tracks.py`,
`tests/test_coverage_integration.py` — 22 теста. Проверяют: выбор направления вдоль
длинной стороны прямоугольника и его поворот вместе с фигурой; штраф за ветер,
переключающий выбор направления при близких по ширине вариантах; декомпозицию
прямоугольника с дырой (ячейки без дырок, без перекрытий, суммарная площадь
сохраняется), мультиполигон (покрыты обе несвязные части), фильтрацию сколов
`min_cell_area_m2`; генерацию галсов для повёрнутой ячейки (курс совпадает с
направлением ячейки), разбиение галса на несвязные отрезки на невыпуклых (L- и
U-образных) ячейках, сохранение суммарной длины при `split_long_track`; и сквозной
прогон `geometry.compute_working_area → coverage.boustrophedon_cells → generate_tracks
→ split_long_track` на сцене с бесполетной зоной.

### `uav_planner.api` — первая версия веб-интерфейса (модуль «Обстановка»)

Реализует backend и фронтенд Экрана 1 и Экрана 2 документа `docs/trebovania/Интерфейс.md`
и функциональные требования `docs/trebovania/Обстановка.md` (ОБС.ФТ.2–4, ОБС.ФТ.8–10).

- **`models.py`** — pydantic-схемы: `ValidationIssue`, `LayerCounts`, `EnvironmentSummary`,
  `EnvironmentDetail` (наследует `EnvironmentSummary`, добавляет `layers` — GeoJSON-объекты
  по слоям для отображения на карте).
- **`service.py`** — вся логика проверки: `validate_and_store(geojson, name)` группирует
  Feature по свойству `layer`, для полигонов вызывает `geometry.validate_polygon()` и
  строит `HeightRange`/`TimeWindow` (ОБС.ФТ.2, ОБС.ФТ.4), для точек ВПП/резервных площадок
  проверяет принадлежность разрешенному пространству и БПЗ через `geometry.Projector` и
  `NoFlyZone.footprint()` (ОБС.ФТ.3). Невалидные объекты не отбрасываются — помечаются
  `properties["_valid"] = False` и возвращаются вместе с валидными, чтобы фронтенд мог
  показать их на карте красным (ИНТ.ФТ.7). Для бесполетных зон с буфером в свойства
  добавляется точный контур буфера (`_buffer_geojson`), посчитанный тем же кодом, что и
  расчётное ядро — не аппроксимация на стороне фронтенда. Хранилище — словарь в памяти
  процесса (`_store`); `list_environments()`, `get_environment()`.
- **`routes.py`** — три эндпоинта: `POST /api/environments` (загрузка), `GET /api/environments`
  (список), `GET /api/environments/{id}` (детали со слоями); документация OpenAPI генерируется
  автоматически FastAPI (`/openapi.json`, `/docs`).
- **`app.py`** — собирает FastAPI-приложение и монтирует статический фронтенд на `/`.
- **`static/index.html`** — фронтенд без сборки (Leaflet с CDN, vanilla JS); подложка карты —
  спутниковые снимки Esri World Imagery (по запросу пользователя — явно не OpenStreetMap;
  до этого пробовали CARTO Positron, но та тоже построена на данных OSM, просто иначе
  раскрашена, поэтому не подходила под явное требование «не OpenStreetMap»), без API-ключа,
  обязательная атрибуция Esri указана в коде. При запуске приложение сразу открывает каталог
  (вкладка «Парк», см. раздел «Новое меню слева» ниже), а не пустую карту с кнопкой
  «Загрузить данные», как было раньше. После загрузки обстановки — Экран 2: слои на карте (ВПП, резервные
  площадки, разрешённое пространство, БПЗ с буфером, препятствия), легенда с чекбоксами,
  боковая панель со сводкой или списком ошибок, индикатор этапа сценария (степпер), история
  загруженных обстановок. Кнопка «Далее: Задача» — плейсхолдер (модуль «Задача» ещё не
  реализован).

Тесты: `tests/test_api_environments.py` — 12 тестов через `fastapi.testclient.TestClient`,
включая самопересечение полигона, отсутствующий диапазон высот, ВПП вне разрешённого
пространства, ВПП внутри буфера БПЗ, наличие `_buffer_geojson`, отдачу фронтенда. Дополнительно
сценарий проверен вручную реальным HTTP-запросом к запущенному `uvicorn` (не только через
`TestClient`).

#### Загрузка обстановки из KML (`uav_planner.kml`)

По запросу пользователя `POST /api/environments` принимает не только GeoJSON, но и KML —
формат определяется по первым байтам файла (`<?xml`/`<kml`), а не по расширению или
Content-Type (ненадёжны на стороне клиента); KML превращается в тот же самый GeoJSON
FeatureCollection и дальше идёт по тому же самому пути валидации, что и раньше — второго
хранилища или отдельной ветки бизнес-логики нет.

Разбор рассчитан не на весь стандарт KML, а именно на те виды файлов, что даны в кейсе
(`docs/examples`, см. `Описание файлов.docx`), — попытка поддержать произвольный KML сразу
означала бы гадать на форматах, которых в руках еще не было:

- **зоны ограничений** ("Московская зона.kml"): `Placemark` с `ExtendedData`
  {`Name`, `Altitudes`, `Type`} → слой `no_fly`. Диапазон высот в файле — свободный текст без
  стандартного формата (это прямо оговорено авторами примера: «предложите свой») —
  `kml.altitude_text.parse_altitude_range` разбирает конструкции вида «От FL280 до FL400»,
  «От земли до 300 м (1000 фут) AMSL», «На всех высотах» (эшелон FL — сотни футов истинной
  высоты; число перед «м» берётся как есть, а не как обратный перевод из футов в скобках).
  Дальше этот диапазон не сохраняется (у `no_fly` в нашей модели нет высоты — это столб на
  всех высотах, см. `NoFlyZone`), а используется для отбора: большинство реальных зон
  ограничений актуальны только для больших эшелонов, до которых БВС не долетит, и
  импортировать их как обычный `no_fly` означало бы заблокировать под ними всю площадь без
  всякой причины (файл почти целиком превратился бы в «здесь летать нельзя»). Зона
  импортируется, только если её нижняя граница ниже практического потолка парка (500 м, см.
  `FLEET_MODELS`) — на "Московская зона.kml" это 299 зон из 341 (реально проверено, не
  оценка). Объекты, которые сам файл явно помечает как `"Некорректная геометрия!"` (например,
  UUR201, UUR244 — 8 из 341), импортируются, но с ошибкой валидации, — это уважение к отметке
  источника данных, а не только к тому, что поймает `shapely.is_valid` (тонкое
  самопересечение может и не быть невалидным по критериям OGC, но авторы данных знают точно).
  Условие активации у части зон ("временное ограничение… в период выполнения полетов в районе
  аэродрома X") зависит от чужой активности, а не от календарной даты/времени суток, и не
  сводится к `TimeWindow` — v1 честно не пытается это распарсить и импортирует такие зоны как
  действующие всегда (консервативно: активна всегда — это надежнее, чем ошибочно посчитать
  неактивной).
- **высотные препятствия** ("obstacles_Московская область.kml",
  "высотные препятствия Приморский край.kml") → слой `obstacle`. `Placemark` с экструдированным
  (`extrude=1`) `Polygon` или `LineString`; высота — Z-координата вершин. `LineString`
  (например, пролёт ЛЭП) оборачивается в тонкий полигон-буфер (1 м, `Projector`), потому что
  наша модель ждёт полигон-footprint для каждого препятствия, а не линию. **v1-упрощение**:
  `altitudeMode` игнорируется, Z всегда трактуется как высота над землёй — примерно у половины
  объектов в обоих файлах (`absolute`/`relativeToSeaFloor`, реально посчитано: 2612 из 5164 в
  московском файле, 2777 из 3201 в приморском) Z по стандарту KML означает высоту над уровнем
  моря, а не высоту самого препятствия, и без модели рельефа (которой у сервиса нет и не
  планируется) отделить одно от другого невозможно. Выбранное допущение систематически
  завышает высоту таких препятствий (на высоту рельефа в точке) — то есть ошибается в
  консервативную, безопасную сторону.
- **прочее** — "Границы полетов.kml" (696 полигонов без названий, типов и высот) этим модулем
  не распознаётся вовсе, сознательно: по смыслу (см. docx) это пример области облета для
  модуля «Задача», а не для «Обстановки», и добавлять для него отдельный, ничем не
  подтверждённый маппинг на слой `airspace` с придуманным потолком высоты означало бы
  импортировать «на глаз» то, чего в файле нет.

Тесты: `tests/test_kml_import.py` — 22 теста (парсер, разбор свободного текста высот,
классификация зон/препятствий, интеграция через `POST /api/environments`) на синтетических
KML-фрагментах тех же форматов. Дополнительно все три реальных файла кейса (Московская зона,
оба файла препятствий) загружены через живой `docker compose` стек и дали ожидаемый результат
(см. числа выше) — один реальный дефект найден и исправлен по ходу: часть координат в
"obstacles_Московская область.kml" записана с пробелом после запятой ("0.0, 0.0, 0.0"), что
рвало наивное разбиение по пробелам (`kml.parser._parse_coordinates` теперь нормализует это
перед разбором, тест на регресс — `test_parses_coordinates_with_space_after_comma`).

### `uav_planner.api` — модуль «Задача» (Экран 3 интерфейса)

Реализует backend и фронтенд Экрана 3 документа `docs/trebovania/Интерфейс.md` и

  облета (`area`, GeoJSON) уже в сводке, а не только в детали — нужно для миниатюры карты на
  карточке вкладки «История» (см. ниже), без отдельного запроса на каждую задачу. По запросу
  пользователя добавлены `fleet_id`/`fleet_name` — задача теперь ссылается на конкретный парк
  БВС (выбирается при постановке, см. вкладку «Создать задачу» ниже), а не использует
  единственный глобальный парк, как раньше.
- **`task_service.py`** — `_validate()` — общая для создания и редактирования проверка:
  обстановка существует и корректна; **парк существует и корректен, и совместим с
  обстановкой по расстоянию** (`_check_fleet_environment_compatibility()` — новое, по
  запросу пользователя: геодезическое расстояние, `geometry.geodesic_distance_m`, эллипсоид
  WGS-84, между локацией парка и центроидом объединения зон `airspace` обстановки
  (`environment_service.environment_location()`); порог — `MAX_FLEET_ENVIRONMENT_DISTANCE_KM
  = 150` км, честно объявленная v1-константа, не значение из ТЗ; если у обстановки нет ни
  одной валидной зоны `airspace` — сравнивать не с чем, проверка пропускается, это уже
  отдельная ошибка поля `area`); тип съемки и GSD (ЗАД.ФТ.4); критерий и вес α для
  «Компромисса» (ЗАД.ФТ.5); начало окна работ не позже конца (ЗАД.ФТ.3, блокирующая часть);
  валидность полигона области и его пересечение с объединением зон разрешенного пространства
  обстановки через `geometry.Projector` (ЗАД.ФТ.2). `_daylight_warning()` — предупреждение
  (не блокирует сохранение), если окно работ не пересекается со световым днем
  (`schedule.daylight_window_utc_hours`) для координат центроида области и даты — вторая,
  неблокирующая часть ЗАД.ФТ.3. `create_task()`/`update_task()` — второй проверяет
  `expected_version == текущая версия` и статус «Черновик», иначе `TaskConflictError`/
  `TaskNotEditableError` (ЗАД.ФТ.12); `fleet_id`, как и `environment_id`, не редактируется —
  переиспользуется из существующей задачи.
- **`task_routes.py`** — `POST/GET /api/tasks` (`POST` — форма теперь принимает и `fleet_id`),
  `GET/PUT /api/tasks/{id}` (`PUT` — form-data с `expected_version`); область облета всегда
  передается на сервер файлом (`area_file`) — бэкенду не важно, собран ли этот файл загрузкой
  или рисованием на клиенте, проверки ЗАД.ФТ.2 одинаковы для обоих способов.
- **`static/index.html`** — Экран 3 (список задач одной уже открытой обстановки,
  `renderTaskListSidebar()`) остался текстовым списком, как и был; его кнопка «Создать
  задачу» больше не открывает старую форму напрямую, а ведёт в новую вкладку «Создать
  задачу» (см. ниже) с уже предзаполненной текущей обстановкой. Форма
  создания/редактирования (`renderTaskFormSidebar`/`submitTaskForm`) используется теперь
  только для **редактирования** существующей задачи (`fleet_id` там не меняется — сервер и
  так не позволяет). v1-ограничение: ЗАД.ФТ.7 (строка поиска по названию и фильтр по статусу
  над списком) по-прежнему не реализован.

### `uav_planner.routing` — кластеризация по площадкам, TSP-тур, балансировка узкого места

Вторая версия модуля `routing` (первая была чистым LPT — длинные галсы первыми на наименее
загруженный БВС, без учёта географии площадок). Сейчас — адаптация схемы «взвешенный
K-Means + m-TSP внутри кластера + балансировка узкого места» под нашу задачу
(min-max время выполнения — критерий J1, «Время»):

- **Шаг 2 (кластеризация).** В классическом K-Means центроиды на каждой итерации
  пересчитываются как среднее точек кластера. Для нас это физически бессмысленно — центроид
  кластера — реальный аэродром конкретного БВС (`Vehicle.launch_point`), самолёт не может
  «переехать». Поэтому центроиды не двигаются: это не итеративный Lloyd's, а взвешенное
  (штраф — стоимость перелёта от площадки) закрепление галса за ближайшим по стоимости БВС
  с поправкой на его текущую загрузку — содержательно то же самое, что K-Means с
  фиксированными центроидами (`_assign_to_nearest`). Если аэродромов меньше, чем БВС, — не
  особый случай: центроид у нас на **экземпляр БВС**, а не на аэродром, так что несколько
  БВС с одной площадки естественно дают несколько кластеров с общим центроидом.
- **Шаг 3 (m-TSP с фиксированным стартом).** Вместо генетического алгоритма (DEAP) или
  Google OR-Tools — оправданных для сотен точек и жёстких ограничений — эвристика «ближайший
  сосед + 2-opt» (`_tsp_order`): для типичных сцен (десятки галсов на БВС) находит разумный
  тур за миллисекунды, без новой тяжёлой зависимости. У каждого галса, как и раньше, два
  допустимых направления прохода.
- **Шаг 4 (балансировка узкого места).** Пока разброс T_total между БВС (по прямолинейной
  оценке — та же, что и раньше в Split) больше `balance_epsilon_s`, «граничный» галс
  (последний в туре самого нагруженного БВС — эвристически близкий к границе кластера, без
  точного геометрического поиска) переносится наименее нагруженному, у кого он вообще по
  силам соло, оба тура перестраиваются; итерации ограничены (`max_balance_iterations`),
  сходимость для произвольной геометрии не гарантируется, но на практике несколько шагов
  заметно выравнивают загрузку — а значит и J1 (min-max), напрямую.
- **Разбиение на вылеты по бюджету** (`_split_into_sorties`, бывший Split) — без изменений
  по сути: режет уже готовый тур на вылеты, резервируя переход до следующего галса и
  обратно на площадку на каждом шаге, чтобы вылет укладывался в бюджет.

- **`cluster.py`** — `Vehicle` (id, скорость, бюджет вылета, своя площадка `launch_point`,
  UTM), `Track` (галс, метры UTM), `Sortie`, `RoutingResult`.
  `cluster_assign_and_route(tracks, vehicles, max_balance_iterations=6, balance_epsilon_s=90.0)`
  — вызывает Шаги 2-4 по порядку. Галс, не помещающийся в бюджет ни одного БВС даже как
  единственный в отдельном вылете, возвращается в `unassigned_tracks` (диагностика
  невыполнимости, не ошибка).
- **Нюансы задачи, из-за которых схема адаптирована, а не взята дословно** (честно, в
  docstring `cluster.py`): БВС ограничен не «за один раз», а вылетает несколько раз (замена
  АКБ) — кластер режется на вылеты уже после балансировки, тем же Split, что и раньше;
  переходы на Шагах 2-4 оцениваются по прямой, без обхода зон — настоящий обход строит
  `visibility.find_path` уже после маршрутизации (`api.plan_service._build_sortie_legs`), и
  по нему пересчитывается точный налёт каждого вылета перед расписанием — небольшой
  остаточный разрыв между оценкой и фактическим обходом ловит независимая проверка
  `safety.check_energy`; итоговый критерий J1 — это makespan **расписания** (со световым
  днём и многодневностью), а Шаг 4 балансирует по T_total (сумме прямолинейных оценок) как
  по сильной приближённой прокси — пересчитывать полное расписание внутри цикла
  балансировки было бы дорого и не нужно для выбора, что переносить; разворотов Дубинса нет
  — это забота нереализованного модуля `motion`.

Тесты: `tests/test_routing_cluster.py` — 12 тестов: балансировка нагрузки между БВС на общей
площадке, разбиение на несколько вылетов при превышении бюджета, недопустимость
нулевой/отрицательной скорости и бюджета, галс длиннее любого бюджета — в
`unassigned_tracks`, переход до далёкого галса реально расходует бюджет (галс, который по
длине бы поместился, становится невыполнимым из-за пути к нему), тот же галс помещается при
увеличенном бюджете (с точным ожидаемым налётом с учётом переходов), второй галс уходит в
отдельный вылет, если добавить его к первому означало бы слетать в противоположные стороны
без «экономии по пути», у двух БВС с разными площадками каждый решает свой ближний галс
почти без транзита, TSP-тур короче наивного порядка обхода, и — балансировка узкого места
реально уменьшает разброс загрузки между БВС (сравнение с отключённой балансировкой,
`max_balance_iterations=0`), не теряя и не дублируя галсы.

### `uav_planner.schedule.timeline` — расписание вылетов

Дополняет `daylight_window_utc_hours` полноценным планировщиком времени: раскладывает
вылеты одного БВС по дням, в пересечении окна оператора и светового дня, с накладными
расходами между вылетами (замена АКБ/подготовка, по умолчанию 15 мин — принятое допущение).

- **`timeline.py`** — `ScheduledSortie`, `ScheduleError` (вылет физически не укладывается ни
  в один день в разумном горизонте — например, длиннее самого длинного возможного светового
  дня; ограничение `max_days` защищает от бесконечного цикла, полярная ночь длится не
  вечно). `assign_timestamps(sorties, lat, lon, start_date, ...)` — если вылет не помещается
  до конца сегодняшнего окна, переносится на начало следующего подходящего дня.

Тесты: `tests/test_schedule_timeline.py` — 6 тестов: вылет в пределах дня, накладные
расходы между вылетами, перенос на следующий день при нехватке окна, соблюдение границ
окна оператора, `ScheduleError` для невозможного вылета, пустой список вылетов.

### `uav_planner.visibility` — обход запрещенных зон на переходах (сеточный A*)

Заменяет прямую линию на переходах (площадка→галс, между галсами, галс→площадка) маршрутом
в обход бесполетных зон и высотных препятствий — но только там, где прямая линия их
действительно пересекает; если прямая уже свободна, сетка вообще не строится.

- **`astar.py`** — `find_path(start, goal, obstacles, cell_size_m=20.0) -> PathResult`.
  Метод: локальная сетка только вокруг отрезка `start-goal` (не по всей сцене) → A*
  (8-связность, эвклидова эвристика, запрет срезать по диагонали через угол занятой
  ячейки) → спрямление сеточного пути («string pulling») жадным поиском прямой видимости
  по точной геометрии препятствий, а не по сетке — путь огибает углы препятствий, а не
  идёт «лестницей». `PathResult.detoured` — потребовался ли обход; `PathResult.fallback` —
  обход не найден (перекрытая прямая возвращена как есть; реальное пересечение поймает
  `safety.check_geozones`).
- Известные упрощения первой версии (в docstring `astar.py`): сетка, а не граф видимости по
  вершинам препятствий — точность обхода ограничена размером ячейки, для очень узких
  проходов путь может не найтись даже при его существовании; размер сетки ограничен
  (`MAX_GRID_DIM`), на очень длинных переходах шаг сетки автоматически укрупняется; не
  проверяет, что маршрут остаётся в разрешённом воздушном пространстве — это отдельно,
  `safety.check_allowed_space`.
- Реальный найденный и исправленный баг при разработке: тест занятости ячейки
  (`prepared.intersects(cell_box)`) считал занятой любую ячейку, лишь касающуюся границы
  препятствия (частый случай для осепараллельных БПЗ и сеточных ячеек) — это ложно
  блокировало обходные колонны точно впритык к границе зоны. Исправлено небольшим отступом
  внутрь тестового прямоугольника ячейки.

Тесты: `tests/test_visibility_astar.py` — 6 тестов: прямая используется как есть без
препятствий и при дальнем препятствии, реальный обход близкого препятствия (маршрут не
заходит внутрь, длиннее прямой), спрямление даёт компактный путь, а не «лестницу»,
`fallback=True` при полностью окружённой цели, старт/цель у самой границы препятствия не
мешают поиску.

### `uav_planner.api` — модуль «Планирование» (Экран 4)

Реализует backend и фронтенд документа `docs/trebovania/Планирование.md` (ПЛН.ФТ.2-3,
ПЛН.ФТ.5-10) — оркестрирует уже готовые модули в сквозной, честный, но **упрощённый**
расчёт. Известные упрощения первой версии (документированы также в docstring
`plan_service.py`):

- **одна модель БВС на план** (смешанный парк в одной задаче — будущая версия) — но какая
  именно модель, решает не «больше готовых экземпляров», а честное сравнение (ПЛН.ФТ.2): для
  каждой подходящей по нагрузке группы (модель, камера) строится **полный кандидат плана**
  (своя рабочая область, галсы, распределение, налёт), и побеждает тот, что минимизирует
  критерий задачи — нормированная взвешенная сумма `J = α·J1/J1* + (1-α)·J2/J2*`
  (Математическая_модель.md, раздел 13; `J1*`/`J2*` — лучшие значения среди посчитанных
  кандидатов), а не размер группы. Например, один быстрый и выносливый Геоскан 201 победит
  три медленных Gemini, если так быстрее/меньше налёт;
- **крейсерская скорость** = паспортный максимум модели минус скорость ветра задачи, без
  учёта направления — консервативная оценка «ветер всегда встречный», до полной модели
  ветра в модуле `motion` (пока не реализован);
- **переходы между галсами и до площадки** — обходят бесполетные зоны и высотные препятствия
  сеточным A* (`uav_planner.visibility.find_path`), а не идут по прямой вслепую, и **учтены в
  бюджете и налёте вылета** (не только в отображении маршрута — см. `uav_planner.routing`
  выше); направление прохода каждого галса по-прежнему выбирается по тому, какой конец
  геометрически ближе к текущей точке (без учёта реальной длины обхода — точного пересчёта
  «а что если развернуть» нет), а порядок самих галсов внутри вылета теперь оптимизируется
  TSP-эвристикой на этапе `routing` (ближайший сосед + 2-opt) — не идеально (эвристика, не
  точный солвер), но заметно лучше порядка «как назначили»;
- **площадка старта/посадки — своя у каждого БВС** (ПЛН.ФТ.2, `_instance_launch_point`):
  собственная локация экземпляра (`FleetInstance.location_lat/lon` из парка), если задана;
  иначе — **ближайшая** к области облета ВПП обстановки (не первая попавшаяся); если ВПП в
  обстановке нет вовсе — центроид области облета. Разные БВС одного плана естественно летают
  с разных площадок, если физически там стоят — отдельного шага «выбрать одну площадку на
  весь план» нет;
- **расчёт** запускается один раз на каждого кандидата (обычно 1-3 группы, по числу моделей с
  подходящей камерой); для тестовых сцен — доли секунды на кандидата, `POST /api/plans`
  успевает дождаться результата в теле того же HTTP-запроса и вернуть его как раньше. Для
  сцен реального масштаба (до 30 минут, `GALS_PLAN_TIME_LIMIT_S`) расчёт уходит в фоновую
  работу — Celery-воркер (`jobs/tasks.py`) — и эндпоинт отдает `202` с объектом работы;
  фронтенд опрашивает `GET /api/plan-jobs/{id}` и показывает прогресс с возможностью отмены
  (см. «Новое меню слева» ниже). Это перенесено из ветки `merge-core-into-wrapper` при
  переносе продуктового стека в `main` — раньше это был честно объявленный пробел.
- **LiDAR и геофизическая съёмка** — не поддерживаются (нет камерных профилей), явная ошибка
  422 с объяснением, а не молчаливый неверный результат.

Независимая проверка результата на нарушения (геозоны, энергия, разведение и т.д.) —
отдельный модуль «Проверка безопасности» (см. ниже), не встроена в сам расчёт.

Модули:
- **`plan_models.py`** — `PlanSortie` (БВС, время старта/финиша, налёт, дистанция, маршрут
  как GeoJSON `LineString` в WGS-84, список `phases`), `PlanSortiePhase` (этап вылета: метка,
  вид «transit»/«survey», интервал времени, дистанция — взлёт и перелёт до зоны, каждый галс,
  переходы между ними, возврат и посадка), `PlanSummary`/`PlanDetail` (версия, J1/J2, модель
  БВС, число вылетов, предупреждения).
- **`plan_service.py`** — `create_plan(task_id)`: группирует готовый парк по (модель, камера)
  с подходящей нагрузкой (`_group_by_model_camera`), для **каждой** группы строит полный
  кандидат плана (`build_candidate` — вложенная функция: высота и шаг галсов (`camera`),
  рабочая область (`geometry`), декомпозиция и галсы (`coverage`), кластеризация по
  площадкам + TSP-тур + балансировка узкого места + разбиение на вылеты по бюджету
  (`routing.cluster_assign_and_route`), точный пересчёт налёта по фактическому маршруту
  в обход зон (`_build_sortie_legs` — раскладывает вылет на этапы: взлёт и перелёт до зоны,
  каждый галс, переходы между ними, возврат и посадка; переходы строит `visibility.find_path`),
  расписание (`schedule`) уже по точной, а не оценочной длительности, метрики J1/J2), и в
  конце выбирает лучшего кандидата по критерию задачи (`_pick_best_candidate`, ПЛН.ФТ.2).
  Площадку вылета/посадки каждого экземпляра БВС считает `_instance_launch_point` — один раз
  для всего парка, до перебора кандидатов (от группы не зависит). Собирает маршрут
  (`track_geojson`) и подробное расписание по этапам (`phases`, с абсолютными
  `start_utc`/`end_utc` каждого этапа) из тех же самых этапов. Если хотя бы один переход не
  удалось обвести (обход не найден в пределах локальной сетки) — в `PlanDetail.warnings`
  добавляется явное предупреждение; если кандидат в принципе не считается (пустая рабочая
  область, нет галсов, ошибка расписания) — этот кандидат просто пропускается, план всё равно
  считается по оставшимся; ошибка возвращается, только если провалились все кандидаты. Каждый
  успешный расчёт — новая версия (`_plan_ids_by_task`), переводит задачу в статус
  «Рассчитана» (`task_service.mark_calculated`).
- **`plan_routes.py`** — `POST /api/plans` (form: `task_id`), `GET /api/plans?task_id=`
  (версии, новые первыми), `GET /api/plans/{id}`. Невыполнимость целиком — `422` с понятной
  причиной; частичная (не все галсы поместились) — `200` с `warnings`, ПЛН.ФТ.10.
- **Попутная правка несогласованности требований**: `Задача.md` (ЗАД.ФТ.11) разрешала
  редактирование только в статусе «Черновик», а `Планирование.md` (ПЛН.ФТ.8) требует
  возможности сменить критерий и пересчитать — по прежней логике это было бы невозможно
  после первого расчёта. Поправил: редактирование запрещено только для «Подтверждена»
  (это уже модуль «Подтверждение и экспорт»); правка параметров задачи возвращает её в
  статус «Черновик» (прежний план остаётся в истории версий).
- **`static/index.html`** — Экран 4: во время расчёта — индикатор в toast; после — карта с
  маршрутом каждого вылета (свой цвет на БВС, легенда), боковая панель с метриками J1/J2,
  списком предупреждений, таблицей расписания (БВС/старт/финиш/налёт) и списком версий
  плана (клик — переключение отображаемой версии); кнопка «Пересчитать». **Клик по строке
  расписания** раскрывает подробность по этапам этого вылета (ИНТ.ФТ.15): «Взлёт с площадки
  «...» и перелёт до зоны выполнения задания» с интервалом времени и дистанцией, «Галс N»,
  «Переход к галсу N+1», «Возврат и посадка на площадке «...»» — стык в стык, без разрывов;
  одновременно маршрут этого вылета на карте выделяется (толще, ярче, поверх остальных), а
  маршруты остальных вылетов бледнеют (`ROUTE_DIM_COLOR`, `applySortieHighlight()`) — можно
  раскрыть сразу несколько строк, тогда все их маршруты остаются выделены одновременно, а
  бледнеют только нераскрытые; свёртывание строки возвращает маршрут в обычный цвет, когда
  раскрытых строк не осталось — все маршруты снова обычного цвета. На карточке задачи
  «Рассчитать» теперь запускает реальный расчёт, «Посмотреть план» —
  открывает последнюю версию для задачи в статусе «Рассчитана».

Тесты: `tests/test_api_plan.py` — 17 тестов: успешный расчёт, перевод задачи в «Рассчитана»,
маршрут в ответе `GET /api/plans/{id}`, вторая версия при повторном расчёте, невыполнимость
без парка / без совместимой нагрузки / для LiDAR, площадка = центроид без ВПП в обстановке,
404 для неизвестной задачи/плана, более высокая скорость ветра действительно увеличивает J2
при том же покрытии, переход от ВПП до области облета реально обходит стоящую на прямой линии
бесполетную зону (маршрут не пересекает её контур, без предупреждений об откате на прямую),
этапы вылета покрывают весь налёт без разрывов и наложений (первый этап начинается ровно в
`start_utc` вылета, последний заканчивается ровно в `end_utc`, соседние этапы стыкуются
секунда в секунду, первый этап — «Взлёт», сумма дистанций этапов равна `distance_m` вылета),
три теста на ПЛН.ФТ.2 (один быстрый Геоскан 201 побеждает группу из трёх медленных Gemini по
критерию «Время», хотя экземпляров у него меньше; площадка выбирается действительно
ближайшей к области облета, а не первой в файле обстановки; собственная локация экземпляра
из парка побеждает более близкую площадку обстановки, если задана явно), и — два БВС на
противоположных концах вытянутой области облета реально делят работу между собой (оба
участвуют, ни один не остаётся почти без дела — `routing.cluster_assign_and_route`,
кластеризация по площадкам + балансировка). Дополнительно проверено вручную реальным
HTTP-запросом (обстановка с двумя ВПП и БПЗ на пути → парк из разных моделей и локаций →
задача → расчёт → побеждает более быстрая модель, площадка —
ближайшая).

### `uav_planner.safety` — независимая проверка безопасности (семь критериев)

Реализует Таблицу 1 `docs/trebovania/Проверка_безопасности.md` (БЕЗ.ФТ.2) — семь чистых
геометрических/временных проверок результата планирования, формально описанных в
Математическая_модель.md, раздел 15. Модуль не переиспользует внутренний код `routing`/
`coverage`/`plan_service` — только их заявленный результат (маршруты, расписание,
заявленные параметры камеры/скорости/бюджета), поэтому проверка действительно независима:
ошибка в допущениях ядра не повторится незамеченной в проверке.

- **`checks.py`** — `discretize(line, step_m)` (точки вдоль маршрута с заданным шагом,
  включая оба конца); `check_geozones`, `check_allowed_space`, `check_energy`,
  `check_reachability`, `check_coverage`, `check_daylight`, `check_separation` — каждая
  возвращает `CheckResult(name, passed, violations)` с человекочитаемыми причинами (до 5,
  дальше — «...и еще N нарушени(й)»). Каждое нарушение — `Violation(message, point)`, где
  `point` (в UTM) — координата «опасного момента» там, где это осмысленно (место пересечения
  геозоны, точка нехватки энергии/недостижимости площадки, представительная точка непокрытого
  участка, место сближения БВС) — нужна интерфейсу для отметок на карте (БЕЗ.ФТ.4).
- **`check_energy`** проверяет фактическую длину маршрута целиком (включая переходы) против
  бюджета — `routing`/`plan_service` тоже теперь учитывают переходы (см. раздел про
  `uav_planner.routing` выше), но при разбиении на вылеты (Split) переходы оцениваются по
  прямой, а настоящий обход зон (`visibility.find_path`) обычно чуть длиннее — эта проверка
  вскрывает именно такой остаточный, узкий, но реальный разрыв, а не грубое отсутствие учета
  переходов, как было раньше.
- **`check_separation`** сравнивает позиции разных БВС (интерполяцией по маршруту с
  постоянной скоростью) в перекрывающиеся по времени интервалы — вскрывает другой реальный
  пробел: маршрутизация (`routing.cluster_assign_and_route`) распределяет и балансирует по
  времени вылета каждого БВС, но не учитывает пространственно-временную координацию между
  БВС (сближение курсов), даже если те стартуют с одной и той же площадки (что по-прежнему
  возможно — у разных БВС может быть общая площадка).
- **`check_reachability`** сверяет площадки посадки только из обстановки (`launch_site` +
  `reserve_site`), а не из собственной локации каждого экземпляра БВС (`FleetInstance.
  location_lat/lon`, используется в `plan_service._instance_launch_point`) — если план
  планирования отправил БВС на локацию, не зарегистрированную как площадка в обстановке, эта
  проверка честно сообщит о недостижимости в конце маршрута, а не притворится, что долёт
  куда угодно — это правильно, а не пробел: посадка должна быть на признанной площадке.

Тесты: `tests/test_safety_checks.py` — 22 теста на всех семь функций и `discretize`
(включая найденную и исправленную реальную ошибку на единицу в `discretize`: терялась
последняя точка маршрута при делении длины на шаг нацело).

### `uav_planner.api` — модуль «Проверка безопасности» (Экран 5)

Реализует backend и фронтенд документа `docs/trebovania/Проверка_безопасности.md`
(БЕЗ.ФТ.1, 3-6). Для независимости проверка заново разбирает слои обстановки и задачи
собственным кодом (не переиспользует парсинг `plan_service`), но доверяет заявленным
физическим параметрам плана (`model_key`, `camera_key`, `height_m`, `swath_m`,
`cruise_speed_mps`, `budget_s` — добавлены в `PlanDetail` именно для этой независимой
проверки) и отдельному полю `PlanSortie.survey_tracks_geojson` (только галсы, без
переходов — нужно для честной проверки покрытия отдельно от маршрута целиком).

Известные упрощения первой версии (документированы также в docstring `safety_service.py`):

- **автоматический пересчет (БЕЗ.ФТ.3)** — при нарушении вызывает `plan_service.create_plan()`
  повторно, без каких-либо скорректированных параметров (адаптация «тип нарушения →
  корректировка запроса планированию», описанная в концепции решения, раздел 4Г, не
  реализована). Расчётное ядро детерминировано, поэтому на неизменной задаче повтор почти
  всегда воспроизводит то же нарушение — три попытки, как правило, расходуются впустую, но
  ограничение и счётчик попыток соблюдены честно, а не имитацией успеха.
- **статус «В процессе автоматического пересчета» (БЕЗ.ФТ.5, желтый индикатор)** —
  наблюдаем только когда конвейер БЕЗ.ФТ.3 идёт в фоновой работе (сцены реального масштаба,
  см. «расчёт» выше): пока работа «Выполняется», это и есть внешне видимое промежуточное
  состояние. На быстрых тестовых сценах, где `POST /api/safety-checks` укладывается в окно
  синхронного ответа, промежуточное состояние по-прежнему не успевает стать наблюдаемым —
  весь конвейер завершается раньше, чем клиент успел бы его опросить.
- **«Разведение» проверяется на единой высоте** плана (в v1 высота одна на весь план — см.
  упрощения модуля «Планирование»), а не по паре высот двух БВС.

**Ручной override нарушений (по запросу пользователя, расширение поверх ЭКС.ФТ.2)** — у
каждого нарушения в отчете есть чекбокс «принять риск» (`ViolationOut.ignored`); когда
оператор отмечает так ВСЕ нарушения отчета (`SafetyReport.violations_acknowledged`), план
можно подтвердить и экспортировать, несмотря на статус «Черновик» — это осознанное
расширение исходного текста требования, не тихое ослабление проверки: подтверждение при
этом честно помечается (`PlanDetail.confirmed_with_overrides`), а сама проверка безопасности
по-прежнему находит и показывает все нарушения как есть — оператор явно берёт на себя
ответственность за каждое из них по отдельности, а не разом «всё ок». Отметки привязаны к
конкретному отчёту (`SafetyReport.id`), а не к плану/задаче: новый расчёт или повторная
проверка строят отчёт заново и «принято» нужно отмечать снова — раньше принятый риск не
переносится молча на другой результат проверки. См. модуль «Подтверждение и экспорт» ниже.

Модули:
- **`safety_models.py`** — `ViolationOut` (стабильный `id` вида `"geozones__0"`, текст
  причины, опциональные `lat`/`lon` в WGS-84 — координата «опасного момента» для карты,
  `ignored` — отметка оператора), `SafetyCheckOut` (машинное имя, русская подпись из
  Таблицы 1, признак нарушения, список `ViolationOut`), `SafetyReport` (итоговый статус, все
  7 проверок, счётчик `auto_recalc_count`, `violations_acknowledged`).
- **`safety_service.py`** — `check_plan(plan_id)`: полный цикл БЕЗ.ФТ.1+3 (проверка и, при
  нарушении, до трёх автоматических пересчётов подряд в одном вызове); `recheck_plan(plan_id)`
  — БЕЗ.ФТ.6 «Повторить проверку» (повторный вызов проверки без пересчёта); счётчик попыток
  ключуется по `(task_id, task.version)` — правка задачи (новая версия) сбрасывает его
  автоматически, как и требует БЕЗ.ФТ.3. `_violation_out()` переводит точку каждого
  `Violation` (UTM) в WGS-84 тем же `Projector`, что строил остальную геометрию проверки, и
  присваивает стабильный `id`. `set_violation_ignored(report_id, violation_id, ignored)` —
  переключает отметку и пересчитывает `violations_acknowledged`; хранится по `id` отчёта
  (`_reports_by_id`), синхронизируется с `_reports_by_plan`.
- **`safety_routes.py`** — `POST /api/safety-checks` (form: `plan_id`) — полный цикл;
  `POST /api/safety-checks/recheck` — «Повторить проверку»; `GET /api/safety-checks/latest?plan_id=`;
  `POST /api/safety-checks/{report_id}/violations/{violation_id}/ignore` (form: `ignored`).
- **`static/index.html`** — Экран 5: кнопка «Проверить безопасность» на экране результата
  плана; после — карта с маршрутами (как на Экране 4) и панель с построчным результатом
  всех семи критериев (зелёная/красная точка, причины нарушений раскрыты списком), итоговым
  статус-беджем и, при нарушении, кнопками «Повторить проверку» / «Вернуться к задаче»
  (БЕЗ.ФТ.4-6). Каждое нарушение с координатой отмечено точкой на карте
  (`layerGroups.safety_violations`); наведение на точку (или на её строку в панели —
  подсветка работает в обе стороны) оставляет цветной только описание этого нарушения,
  остальные строки и точки бледнеют (`.hl-active`/`.hl-dim`, `highlightSafetyViolation()`
  в `index.html`) — так видно, какая именно опасность где на карте, если их несколько.

Тесты: `tests/test_api_safety.py` — 15 тестов: успешная проверка (все 7 критериев пройдены),
обнаружение неустранимого пересечения с бесполетной зоной с координатами в ответе (WGS-84,
для отметок на карте), исчерпание лимита автопересчётов при устойчивом нарушении (с
проверкой, что отчёт привязан к последней пересчитанной версии плана), «Повторить проверку»
не создаёт новых версий плана, получение последнего отчёта, 404 без предварительной проверки
и для неизвестного плана, отказ «Достижимость площадки» при отсутствии площадки посадки в
обстановке; плюс 5 тестов на ручной override (у каждого нарушения стабильный `id`, изначально
не принято; отметка части нарушений не подтверждает отчёт целиком; отметка всех — подтверждает
(включая сводную строку «...и еще N»), снятие одной отметки снова блокирует, `GET .../latest`
отражает то же состояние; 404 для неизвестного нарушения/отчёта). Дополнительно проверено
вручную реальным HTTP-запросом (обстановка со всеми типами зон и площадок → парк → задача →
расчёт → проверка безопасности с настоящими причинами нарушений и их координатами).

### `uav_planner.api` — модуль «Подтверждение и экспорт» (Экран 6)

Реализует `docs/trebovania/Подтверждение_и_экспорт.md` (ЭКС.ФТ.1-9) — финальный шаг
сценария: статус плана на всём его жизненном цикле, ручное подтверждение оператором плана
без нарушений и экспорт подтверждённого плана в KML/GeoJSON по каждому БВС.

Известные упрощения и несостыковки первой версии (документированы также в docstring
`export_service.py`/`plan_service.py`):

- **нет модели пользователей/аутентификации** — «ФИО» подтверждающего (ЭКС.ФТ.6, ЭКС.ФТ.9)
  вводится оператором свободным текстом в форме подтверждения (фронтенд), а не берётся из
  сессии; при переносе продуктового стека появился облегчённый компромисс на уровне API
  (`api/deps.py`, заголовок `X-User-Name`) для сообщений о конфликте в модуле «Задача» —
  форма подтверждения им не пользуется, поле формы остаётся первичным. Гонка при
  одновременном подтверждении (ЭКС.ФТ.9) разрешается условным `UPDATE` статуса в БД
  (`repositories.sql.PlansRepository.confirm`, допустимые исходные статусы — «Проверен», или
  «Черновик» при принятых нарушениях) — второй запрос получает `409` с указанием, кем план
  уже подтверждён. Предпосылка ЭКС.ФТ.2 («последняя проверка без нарушений») проверяется
  отдельно, по статусу самого отчёта проверки (`SafetyReport.status`), не по статусу плана —
  см. следующий пункт.
- **`PlanDetail.status == "Проверен"` не означает «пройдена без нарушений»** — означает
  «проверка выполнена» (пройдена или не пройдена); отдельного статуса на нарушения в жизненном
  цикле плана нет (ЭКС.ФТ.5 подразумевал ровно две ветки после «Проверен» — «Подтвержден» и
  «Выгружен», третьей для «проверена, но есть нарушения» не появилось). Фактическое условие
  подтверждения читает `SafetyReport.status`/`violations_acknowledged` последнего отчёта, а не
  бейдж плана — интерфейс (Экран 6) устроен так же, см. `renderExportSidebar` в
  `static/index.html`.
- **ЭКС.ФТ.8 ссылается не на тот раздел**: «состав свойств GeoJSON — см. «Методы», раздел 7» —
  в `docs/realization/uav_planner_methods.html` раздел 7 называется «Перелеты и достижимость
  площадок» и такой таблицы не содержит (несостыковка в самом тексте требования, текст не
  правился задним числом). Настоящая таблица (и структура KML) — раздел 15 того же документа
  «Состав экспортируемых файлов», добавленный отдельно и спроектированный на основе уже
  имеющихся полей `PlanSortie`/`PlanSortiePhase`, без каких-либо изобретённых фактов.
- **ключевые точки экспорта восстанавливаются интерполяцией**: `PlanSortiePhase` не хранит
  собственные координаты (только суммарный маршрут вылета) — точки границ этапов честно
  получаются интерполяцией вдоль фактического маршрута пропорционально накопленной дистанции
  этапа; поскольку весь вылет летится на одной крейсерской скорости, это точное восстановление,
  а не приближение.
- **высота в экспорте — константа `height_m` плана**, а не honest-профиль набора/снижения:
  расчётное ядро вообще не ведёт высотный профиль (см. упрощения модуля «Планирование»).
- **неизменность подтверждённого плана (ЭКС.ФТ.3)** обеспечена по построению: в системе нет
  ни одного эндпоинта, который редактирует `PlanDetail.sorties`/`phases` после создания —
  новый результат всегда означает новую версию плана (`plan_service.create_plan`), старая
  остаётся в истории версий неизменной. Подтверждение плана дополнительно переводит связанную
  задачу в статус «Подтверждена» (`task_service.mark_confirmed`) — это блокирует
  редактирование параметров задачи, пока по ней не будет запущен новый расчёт (который снова
  переводит задачу в «Рассчитана», как и предусматривает ЭКС.ФТ.3: «новый расчёт создаёт
  отдельную версию плана»).
- **ручной override нарушений безопасности поверх ЭКС.ФТ.2** (по запросу пользователя, не из
  исходного текста требования) — план с нарушениями обычно подтвердить нельзя, но если
  оператор в модуле «Проверка безопасности» явно отметил принятыми ВСЕ нарушения последнего
  отчёта (`SafetyReport.violations_acknowledged`, чекбоксы у каждого нарушения на Экране 5),
  подтверждение (и вслед за ним экспорт) разблокируется — `export_routes._violations_overridden`
  независимо перепроверяет это условие через `safety_service` на сервере при каждом запросе
  подтверждения, не доверяя клиенту; итог помечается честно
  (`PlanDetail.confirmed_with_overrides`), сама проверка безопасности продолжает находить и
  показывать нарушения как есть — они не «чинятся» отметкой, оператор просто берёт
  ответственность за каждое конкретное нарушение на себя.
